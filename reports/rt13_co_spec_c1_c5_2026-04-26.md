## C1 — Retire-cadence (Φ_P contraction guarantee)

**Definition.** Over any rolling 7-day window, the count of successfully retired (BL ∨ Inv ∨ lesson) entries `Ω_pruned ≥ θ_C1` measured at session boundaries; retirement = `ended` field set + `superseded_by` field set + entry moved to `lessons_archive.md` under temporal-triple pattern. Empty windows (no sessions ran) excluded.

**Threshold.** `θ_C1 = 1` per 7-day window of *active* sessions (≥1 session held). Justification: Analyst EN baseline `Ω_pruned ∈ [0.0, 1.2]` per recent windows — 1.0 sits at the upper bound of observed practice, demanding ≥1 retirement per active week without forcing artificial pruning during dormant periods. Below 1 = `Φ_P` non-contractive (Val-RU §3.2 — Banach contraction requires `k_P < 1` to fire with positive frequency).

**Enforcement mechanism.** Three layers (BL-30 defense-in-depth):
1. **Hook (BLOCK):** `.claude/hooks/retire-cadence-check.sh`, fires on session-start. Reads `lessons_archive.md` + git log of last 7 days; if active sessions ≥ 1 AND `Ω_pruned == 0` for window → exit 1 with message "C1 violation: 0 retirements in 7-day active window; spawn [BUILDER] retire+archive before proceeding."
2. **Bootstrap §9:** Lambda Audit prints `Ω_pruned(7d) = X` in the always-load 7-item checklist (extends meta.md §14 item 9 already declared as always-print in v10).
3. **Hansei trigger:** if hook fires twice in same 30-day window → mandatory Hansei written to `reports/hansei-c1-dormancy-<date>.md` per BL-12.

**Falsifying scenario.** After 14 days of active sessions (≥4 held) with 0 retirements logged AND no hook BLOCK firing AND no Hansei written → C1 enforcement is decorative. Test: `git log --since="14 days" --diff-filter=D -- lessons_archive.md` returns 0 lines with hook silent → FAIL.

**Extension point.** Extends BL-26 ("META always delegates"): retirement is a META Decision routed to `[BUILDER] retire+archive` agent (never META direct edit on `BOOTSTRAP_LESSONS.md` or `lessons.md`); the cadence threshold is the operationalization of Inv 1's "no exception" clause for the retire-class action. The hook is a sibling of `enforce-delegation.sh` (existing pattern).

## C2 — Ordering + Atomicity (D→M→P locked, all-or-none)

**Definition.** β-path Builder spawns MUST follow `D → M → P` sequence at the level of git commits. "All-or-none" = if D fails Validator gate (B < 0.5 OR build-verify fails), M-Builder MUST NOT spawn until D rebuilt or β aborted via δ/γ fallback; same chain D→M→P. The full triplet ships as a single release wave (3 commits, same release window, no interleaved unrelated work).

**Threshold.** Sequence violation tolerance = 0. Concretely: if `git log --reverse --grep="cure-D\|cure-M\|cure-P"` shows P-commit before M-commit, OR M-commit before D-commit, OR any non-cure commit between cure commits → BLOCK release tag.

**Enforcement mechanism.**
1. **Roadmap structure (always-print):** `projects/eradev/roadmap.md` β-path section MUST list 3 phases as ordered list `1. D / 2. M / 3. P` with explicit "predecessor must reach Validator GREEN" gate per phase. Coherent L1 reviews after each Builder ship.
2. **Builder-spawn discipline (META protocol):** before spawning M-Builder, META MUST run Check Agent: "Has D-cure shipped, passed Validator, and been committed with sha SHA_D?" — yes/no. NO → spawn aborted. Same for P after M.
3. **Release-wave hook:** `.claude/hooks/beta-sequence-check.sh` invoked on tag `beta-v1`. Verifies commit topology D→M→P; mismatch → exit 1.

**Falsifying scenario.** β release tag `beta-v1` exists in repo AND `git log --topo-order` between SHA_pre_β and tag shows a non-D→M→P ordering (e.g., M committed before D, OR P committed before M, OR an unrelated commit interleaved) AND `beta-sequence-check.sh` did not block tag creation → C2 enforcement is decorative.

## C4 — Frozen-Snapshot Semantics (D measurement against pre-cure baseline)

**Definition.** D's `leverage_factor` is computed against a **frozen pre-β-ship snapshot** of `framework_state`, NOT against the live state mid-rollout. Snapshot = git commit SHA captured at moment RT-13 closes (this RT round); snapshot file lists all framework-self artifacts present at that SHA. All D measurements during the β release wave reference the snapshot; D recompute against live state resumes only after wave-end (4-session boundary, see C5).

**Threshold.** Boundary precision = 1 commit SHA (no ambiguity). Snapshot file MUST exist before first cure-Builder spawns; absent → BLOCK. Concretely: `.eradev/beta_snapshot.txt` contains `SHA_pre_β=<full-40-char-hash>` and `framework_self_baseline_count=<N>` and `framework_self_baseline_paths=<sorted list>`.

**Enforcement mechanism.**
1. **Pre-β snapshot creation:** RT-13 closure step (this report's commit) writes `.eradev/beta_snapshot.txt` AND tags repo with annotated tag `beta-pre-ship` (immutable per git semantics if pushed). Both required (file + tag = double anchor; BL-30 defense-in-depth).
2. **D-cure hook reads from snapshot:** `leverage-counter.sh` reads `.eradev/beta_snapshot.txt`'s `framework_self_baseline_count` for denominator during β window (commits between `beta-pre-ship` tag and `beta-post-ship` tag). After `beta-post-ship` tag, denominator switches to live `git ls-files`-based count.
3. **B-formula version stamp:** every report written during β window has header line `B-snapshot: Σ_pre` (pre-cure formula); reports written after `beta-post-ship` tag have `B-snapshot: Σ_post`. Validator sweep (existing μ-check) extends to verify header presence.
4. **D self-scoring exemption:** the D-cure ship artifact itself (the spec + Builder commits) MUST be scored under `Σ_pre` (Val-RU §4 resolution). This avoids the self-reference paradox where D's own ship is scored by D's own amendment.

**Falsifying scenario.** Cure-D commit is scored using post-D `leverage_factor` formula (i.e., `B-snapshot: Σ_post` in its Hansei or Validator report) → C4 violated. Test: read `reports/rt-builder-D-2026-04-XX.md` header; if `B-snapshot: Σ_post` present → FAIL. Second falsifier: `.eradev/beta_snapshot.txt` absent at moment of D-Builder spawn → FAIL.

**Extension point.** Extends Inv 6 ("3-fix STOP, write spec, re-run RT-1") — the snapshot IS the spec preserved across the cure window, ensuring the cure does not retroactively change the regime against which it is verified. Extends temporal-triple pattern (`valid_from | ended | superseded_by`) by applying it at the formula level: `B_formula.valid_from = SHA_pre_β` for Σ_pre; `B_formula.ended = SHA_post_β`, `superseded_by = SHA_post_β` for Σ_post. ## Cross-cutting interactions

**C2 atomicity ↔ C5 audit timing.** C2 demands all-or-none ship inside one release wave (3 commits, no interleaving). C5 measures 4 sessions AFTER the post-ship tag. These do not conflict: C2 governs the wave, C5 governs the post-wave window. The boundary tag `beta-post-ship` separates them cleanly. Risk: if C2 partially fails (e.g., D ships, M fails Validator), there is no `beta-post-ship` tag, C5 cannot fire — but this is correct behaviour (no audit needed for an aborted wave; revert path follows γ/δ matrix).

**C1 retire-cadence ↔ C5 T1 test.** C1 demands `Ω_pruned ≥ 1` per 7-day active window in steady state. C5 T1 demands `Ω_pruned ≥ 1` across 4 post-ship sessions. C1 is the *standing* invariant; C5 T1 is the *first instance* of evaluating it on β. No conflict; C5 T1 is a proper subset of C1's continuous obligation. If C1's hook fires (BLOCK on session-start) before the 4-session boundary, C5 T1 auto-passes (because the BLOCK forced a retire).

**C3 ε_meta ↔ C4 snapshot.** C3 enumerates the 6 META outputs; C4 snapshots framework state. The snapshot file `.eradev/beta_snapshot.txt` MUST cite ε_meta (pinning the canonical anchor `CLAUDE.md §META Output Specification`) to prevent ε_meta drift across the β window. If ε_meta is amended mid-β (forbidden), the snapshot becomes stale; this is enforced by Inv 6 (write spec → re-run RT-1) — any ε_meta change requires a new RT round, not a mid-flight edit.

**C4 snapshot ↔ C1 retire actions.** P-cure retires entries during β window. Retired entries change `framework_self_baseline` after the snapshot was taken. Resolution: retire-events during β window are logged to a delta-log (`.eradev/beta_delta_log.txt`) and applied to the live count after `beta-post-ship` tag, not to the snapshot's frozen denominator. D measures against snapshot; live count resumes post-tag (Val-RU §2.2 + §4 — exactly the snapshot semantics this addresses).

**No 4-way conflict.** All pairwise interactions resolve cleanly via tag boundaries (`beta-pre-ship`, `beta-post-ship`) and the canonical ε_meta anchor. Cross-cutting risk: σ ≈ 0.20 (declared honest below).
