# RT-1 Builder: Аналитический отчёт по промптам EraDev

> Роль: СТРОИТЕЛЬ, Команда 1
> Дата: 2026-04-02
> Объём проанализированного материала: 3690 строк в 9 файлах

---

## 1. Общая оценка: система перегружена собственным весом

Общий объём промптов EraDev составляет 3690 строк, из которых eradev.md занимает 1255 строк, meta.md -- 1116 строк, validator.md -- 323 строки, builder.md -- 240 строк, projects/academic-lab.md -- 229 строк, coherent.md -- 199 строк, MEMORY.md -- 172 строки, analyst.md -- 89 строк, visionary.md -- 67 строк. С практической точки зрения Строителя, агент получает задачу и должен прочитать builder.md (240 строк), затем, по инструкции в MEMORY.md, ещё eradev.md (1255 строк), а при необходимости и academic-lab.md (229 строк). Это означает, что прежде чем агент написал хотя бы одну строку кода, он потратил контекстное окно на чтение ~1700 строк инструкций. Это прямое нарушение принципа Muri (перегрузка), который сама система декларирует в eradev.md, строки 400-410.

## 2. Практическая оценка builder.md

Builder.md -- один из наиболее сбалансированных промптов в системе. Строки 1-50 содержат чёткое определение роли, обязанностей и рабочего процесса, это работает хорошо. Секция "Правила кода" (строки 26-42) -- компактная и практичная, даёт конкретные команды для Go, TypeScript и Bash. Security Checklist (строки 53-81) полезен, но избыточен для большинства задач: Строителю, который правит CSS или добавляет UI компонент, не нужно проверять TLS MinVersion и hop-by-hop headers. Блок Jidoka Self-Check (строки 85-93) заставляет агента оценивать "шаблонность" по шкале 1-10 после каждого блока работы. На практике это формальность: агент выдаст "7/10" и продолжит работу, потратив токены на ритуал вместо кода.

Уроки от Meta-Agent (строки 102-240) -- главная проблема builder.md. Паттерны P1-P23 занимают 140 строк, большинство из них описывают конкретные инциденты проекта academic-lab (nginx на порту 443, Radix Dialog pointer-events, Moscow saga), а не универсальные принципы. Строитель, работающий над новым проектом, получит 23 правила, из которых 18 релевантны только для academic-lab. Паттерн P22 (строка 230) "overflow-x:hidden ТОЛЬКО на body" -- это CSS факт, а не архитектурное правило, ему место в snippets или code review checklist, но не в промпте агента.

## 3. Практическая оценка eradev.md

Eradev.md в 1255 строках пытается быть одновременно: (a) инструкцией для Мета-Оркестратора, (b) теоретическим обоснованием системы (ODTOE, TPS, AGI), (c) описанием Round Table процесса, (d) описанием всех механизмов (A3, Bottleneck Expansion, Kill-Switch, Nemawashi, Pull-якорь, Prediction Delta), (e) путём к AGI с формулами и ASCII-диаграммами. Строки 488-535 (ODTOE когерентность) содержат формулы B = F^w1 x E^w2 x (1-sigma)^w3 x Lambda^w4 и коллективной когерентности P_coll, которые ни один агент не вычисляет на практике -- это теоретический фундамент, который тратит контекст агента без практического эффекта. Строки 536-548 (тороидальная топология) описывают внутреннее и внешнее кольцо коммуникации с отсылкой к золотому сечению и теореме KAM -- красиво, но агенту-Строителю это не помогает написать ни одной строки кода. Секция "Путь к AGI" (строки 551-680) с псевдокодом meta-агента и спиральной памятью занимает 130 строк и адресована исключительно Meta-Agent, но находится в общем файле, который читают все.

При этом практически полезные секции -- Round Table описание (строки 722-852), шаблоны запуска агентов, правила параллелизации -- размазаны между eradev.md и MEMORY.md, дублируя друг друга.

## 4. Практическая оценка meta.md

Meta.md -- 1116 строк, из которых примерно 800 строк составляет спиральная память витков 1-5. Секция "Роль" и "Что ты делаешь" (строки 1-55) -- компактная и ясная. Секция "Археология коммитов" (строки 24-121) -- практически полезная, содержит конкретные bash-команды. Однако витки спиральной памяти (строки 157-1116) представляют собой подробнейший анализ каждого инцидента с B-дефицитами, формулами когерентности, мета-мета-анализом и мета-мета-мета-анализом. Виток 3 (строки 338-548) содержит таблицы с 439 коммитами, процентами фиксов по фазам, тренд-анализ -- это ценный материал для человека, но агент Meta-Agent при каждом запуске тратит контекст на перечитывание ВСЕЙ истории инцидентов, а не только актуальных обобщений. Мета-мета-правила MM1-MM5 (строки 283-308) фактически говорят одно и то же разными словами: "обобщай, проверяй полноту, тестируй свои правила". Пять формулировок одной мысли -- это Muda.

## 5. Практическая оценка остальных промптов

Analyst.md (89 строк) -- самый компактный из "ролевых" промптов и при этом один из наиболее эффективных. Шесть правил от Meta-Agent (A1-A6) конкретны и практичны. Единственная проблема: правило A6 (строки 82-86) описывает три подпункта о build pipeline, которые дублируют B9 в builder.md.

Visionary.md (67 строк) -- минималистичный и достаточный. Три правила Vi1-Vi3 от Meta-Agent компактны. Этот файл можно считать образцом правильного размера промпта.

Validator.md (323 строки) -- второй по размеру ролевой промпт после builder.md. Содержит 19 паттернов (P1-P19), причём паттерны P17-P19 (строки 302-319) добавлены из Витка 6 и описывают fix chain detector, revert policy и cross-browser gate -- все три крайне специфичны для mobile/PWA задач academic-lab. Чеклист деплоя (строки 267-298) расширен до 30 пунктов, разбитых на PRE-PUSH, FEATURE FLAG, PROTOCOL CHANGE и POST-DEPLOY. На практике Валидатор, проверяющий CSS-правку, будет прокручивать 30 пунктов, из которых 25 нерелевантны.

Coherent.md (199 строк) -- хорошо структурирован по уровням L1/L2/L3. Decision Log (строки 179-196) -- ценный артефакт, но он превращает промпт в хранилище данных вместо инструкции. При каждом запуске Когерент грузит всю таблицу решений, даже если задача не связана ни с одним из них.

## 6. Дублирование между файлами

Это главная системная проблема. Вот конкретные примеры дублирования:

**"Мета-Оркестратор не делает задачи сам"** -- повторяется в eradev.md (строки 24-48), MEMORY.md (строки 8-25), и кратко в MEMORY.md (строка 139). Три раза одно и то же правило разной степени подробности.

**Железные правила** -- перечислены в eradev.md (строки 24-148), в MEMORY.md (строки 134-143), в academic-lab.md (строки 36-74). Три версии одного списка, причём в academic-lab.md есть правила 1-6 с расширенными пояснениями, в MEMORY.md -- правила 1-8 кратко, в eradev.md -- другая разбивка.

**Классификация задач S/M/L/XL** -- eradev.md (строки 96-109), MEMORY.md (строки 29-37). Две идентичные таблицы.

**File Ownership Protocol** -- eradev.md (строки 111-123), MEMORY.md (строки 119-130). Практически одинаковый текст с примерами.

**Иерархия Когерентов L1/L2/L3** -- eradev.md (строки 150-189), MEMORY.md (строки 109-116), coherent.md (строки 9-47). Три версии одной иерархии.

**Формула ODTOE B = F x E x (1-sigma) x Lambda** -- eradev.md (строки 488-503), MEMORY.md (строки 147-158), academic-lab.md (строка 202). Три повторения формулы.

**Шаблоны запуска агентов** -- eradev.md (строки 757-771), MEMORY.md (строки 52-105). Два набора шаблонов с разным уровнем детализации.

**Андон** -- повторяется дословно в конце каждого ролевого файла (builder.md строка 238, analyst.md строка 87, visionary.md строка 65, validator.md строка 321, coherent.md строка 197). Пять идентичных вставок.

По оценке, от 25% до 30% всего объёма промптов -- дубликаты. Это ~1000 строк, которые тратят контекстное окно агентов на перечитывание уже известного.

## 7. Что слишком длинное и мешает агентам

**eradev.md целиком**. 1255 строк для файла, который агенты читают "на старте сессии" -- это перегрузка. Агент-Строитель, вызванный для задачи "добавь кнопку в компонент", не должен читать теорию AGI и тороидальную топологию. Строки 488-680 (ODTOE теория + AGI путь) можно полностью вынести в отдельный файл theory.md, который читает только Meta-Agent.

**meta.md спиральная память**. Строки 157-1116 -- подробный лог каждого инцидента за 4 сессии. Для Meta-Agent нужны только обобщения (мега-паттерны) и метрики, а не полные B-дефицит расчёты для каждого инцидента. Детали витков 1-3 можно архивировать в spirals/v1.md, spirals/v2.md и т.д., оставив в meta.md только актуальные выводы.

**builder.md паттерны P1-P23**. 140 строк проектно-специфичных правил, из которых при типичной задаче релевантны 3-5. Решение: вынести в checklists/builder-academic-lab.md, оставив в builder.md только универсальные принципы.

**validator.md чеклисты**. Четыре чеклиста по 6-8 пунктов (строки 267-298) + edge case чеклист (строки 161-171) + security audit (строки 48-55) = 50+ пунктов. Валидатор тратит больше контекста на чтение чеклистов, чем на реальную проверку. Нужна фильтрация по типу задачи: если задача UI-only -- грузить UI-чеклист, если infra -- грузить infra-чеклист.

## 8. Предложения по упрощению и ускорению работы агентов

**8.1. JIT-загрузка вместо eager-загрузки.** Вместо "прочитай eradev.md + MEMORY.md + academic-lab.md + builder.md" при старте -- загружать только core.md (30-40 строк с ролью и базовыми правилами) + project-config.md (10-15 строк со спецификой проекта). Остальное подгружать по запросу: если задача связана с TLS -- агент загружает checklists/tls.md, если с autodeploy -- checklists/deploy.md. Это сократит начальную загрузку с ~1700 строк до ~60 строк.

**8.2. Убрать Jidoka Self-Check из промптов агентов.** Агент, оценивающий свою "шаблонность" по шкале 1-10, тратит токены на формальность. Если нужна оценка качества -- это задача Валидатора или Meta-Agent, а не самого Строителя. Строки 85-93 builder.md и аналогичные секции в других промптах -- удалить.

**8.3. Объединить дублирующие секции.** Железные правила должны существовать в ОДНОМ месте (core.md), а не в трёх. Формула ODTOE -- в theory.md, а не в трёх файлах. Иерархия Когерентов -- только в coherent.md, в других файлах ссылка.

**8.4. Андон вынести в core.md.** Вместо пяти копий одинакового текста в каждом ролевом файле -- одно определение в core.md, которое все агенты читают.

**8.5. Сократить спиральную память до обобщений.** Вместо полного лога инцидентов в meta.md -- таблица мега-паттернов MP1-MP13 (те уже есть в academic-lab.md строки 128-181) + ссылки на архивные файлы с деталями витков.

**8.6. Ввести blast radius тег для чеклистов.** Каждый пункт чеклиста помечается тегом LOW/MEDIUM/HIGH/CRITICAL. Мета-Оркестратор при запуске агента указывает blast radius задачи, агент грузит только релевантные пункты.

## 9. Предложение по структуре файлов: ядро vs. проектная специфика

```
eradev/
  core.md                    # 40-50 строк: роль Мета-Оркестратора, S/M/L/XL,
                             # железные правила (единый источник), Андон, ODTOE
                             # краткая формула (3 строки, не 50)

  roles/
    visionary.md             # Роль + универсальные принципы (как сейчас, ~40 строк)
    analyst.md               # Роль + универсальные принципы (~50 строк)
    builder.md               # Роль + правила кода + Security Checklist (~80 строк)
    validator.md             # Роль + универсальные чеклисты (~80 строк)
    coherent.md              # Роль + L1/L2/L3 (~80 строк)
    meta.md                  # Роль + процесс анализа (~60 строк)

  theory/
    odtoe.md                 # Формулы, коллективная когерентность, тороидальная
                             # топология, AGI путь -- для Meta-Agent и для
                             # справки, НЕ для каждой сессии
    tps.md                   # Toyota Production System, Muda/Mura/Muri, Jidoka,
                             # Hansei, A3 -- для понимания философии
    round-table.md           # Полное описание RT-1/RT-2/RT-3 с промптами
    protocols.md             # Kill-Switch, Nemawashi, Bottleneck Expansion,
                             # Session Architecture -- по запросу

  projects/
    academic-lab/
      config.md              # True North, архитектура, ноды, серверы
      rules.md               # Железные правила специфичные для проекта
                             # (autodeploy, nodes.json, zero-hardcode)
      lessons.md             # Уроки 1-20, мега-паттерны MP1-MP13
      checklists/
        deploy.md            # Чеклист деплоя (pre-push, post-deploy)
        tls.md               # TLS/security чеклист
        frontend.md          # Frontend edge cases, browser compatibility
        protocol.md          # Feature flags, canary deploy, protocol changes
      spirals/
        v1.md                # Архив витка 1 (детали инцидентов)
        v2.md                # Архив витка 2
        v3.md                # Архив витка 3
        v4.md                # Архив витка 4
        current.md           # Только обобщения актуального витка

  templates/
    agent-launch.md          # Шаблоны запуска агентов (из MEMORY.md)
    a3.md                    # A3-шаблон кристаллизации
    result-format.md         # Стандартный формат выхода агентов
```

Ключевой принцип этой структуры: агент при запуске читает core.md (50 строк) + свой roles/builder.md (80 строк) + проектный config.md (30 строк) = 160 строк вместо 1700. Дополнительные чеклисты и уроки подгружаются только когда задача их требует.

## 10. Что работает хорошо и не надо трогать

Общая архитектура пяти ролей -- рабочая и логичная. Визионер/Аналитик/Строитель/Валидатор/Когерент -- минимальная устойчивая команда, потеря одной роли действительно компенсируется остальными. Идея Round Table (RT-1/RT-2/RT-3) как трёх точек синхронизации -- практически ценная. Классификация задач S/M/L/XL с разным количеством агентов -- правильный подход, экономит ресурсы на тривиальных задачах. File Ownership Protocol -- критически важный для предотвращения конфликтов при параллельной работе. Мега-паттерны MP1-MP13 -- концентрированная мудрость из 439 коммитов, их нужно сохранить и сделать легко доступными. Blast radius как критерий для выбора стандарта качества -- одна из сильнейших идей системы.

## 11. Резюме: три главных действия

Первое: разделить eradev.md на core.md (50 строк) + theory/ (остальное). Это одно действие сократит начальную загрузку агентов на 90%.

Второе: вынести проектно-специфичные уроки и чеклисты из ролевых промптов в projects/academic-lab/. Это сделает промпты агентов универсальными и пригодными для любого проекта, а не только для academic-lab.

Третье: устранить дублирование, оставив единый источник для каждого правила/определения. Это сэкономит ~1000 строк и устранит риск рассогласования между тремя версиями одного правила.

Система EraDev содержит ценные идеи и рабочие механизмы, но они утоплены в объёме текста, который сама система определила бы как Muri (перегрузка) и Muda (потери). Предложенная реструктуризация сохраняет всё содержание, но делает его доступным по запросу, а не принудительно при каждом запуске агента.
