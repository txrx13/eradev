## Strategic Decision

### The Core Insight

**EraDev's 5 roles are NOT software-specific. They are universal cognitive archetypes wearing software clothing.**

| Current (software vocabulary) | Universal archetype | Software instance | Science article instance | Book instance | Business instance |
|---|---|---|---|---|---|
| Visionary | **Direction** — what and why | Architect | Research question owner | Thematic arc designer | Strategist |
| Analyst | **Decomposer** — what parts | Technical Lead | Methodology designer | Outline architect | Market analyst |
| Builder | **Executor** — materialize | Engineer | Section writer | Chapter drafter | Plan author |
| Validator | **Verifier** — does it hold | QA Engineer | Peer reviewer | Editor | Financial modeler |
| Coherencer | **Synthesizer** — does it cohere | Project Manager | Abstract/discussion author | Narrative integrator | Exec summary writer |

**Empirical validation of n_min = 5:** Google's PaperOrchestra (2026) independently arrived at 5 agents for scientific paper writing: Outline / Plotting / Literature Review / Section Writing / Content Refinement. These map 1-to-1 to EraDev's abstractions. MetaGPT independently converged on 5 roles for software. Two independent teams, two different domains, both converged on n=5. This is empirical evidence of a stable attractor, not a coincidence.

**The universal math already exists:**
- B = F x E x (1-sigma) x Lambda applies to any cognitive work, not just code
- S_team and S_adjusted measure agreement, not compilation
- P_coll measures collective collapse probability — universal
- Round Table is a deliberation pattern, not a git workflow

### What needs to change vs. what does NOT

**MUST change (the surface layer):**
1. Role file vocabulary — rename domain-specific terms ("deployment," "commit," "test suite," "zero-downtime") to universal archetypes
2. CLAUDE.md templates — fork into domain variants (software / article / book / universal)
3. BL-5 ("Zero-downtime is mandatory") — soften to universal "Reversibility required: every irreversible action requires rollback plan"
4. Terminology in eradev.md Section 0 — "implement/fix/build/test/debug/refactor" keyword detection must extend with "write/draft/revise/argue/prove/derive/outline"
5. Role tool-scope permissions (borrow #1) should be PER DOMAIN, not hardcoded

**MUST NOT change (the core):**
1. ODTOE math — already universal
2. 5-role structure — empirically validated as stable attractor
3. Round Table protocol — deliberation pattern is universal
4. Bilingual architecture (BL-19) — language-as-operator is domain-independent
5. 30 Bootstrap Lessons — most are universal meta-patterns (BL-16 Lambda problem applies to any task)
6. 3-Layer identity enforcement — universal anti-drift mechanism
7. Check-First Pipeline (BL-17/21) — already proved itself universal when article work broke software assumptions

### Strategic recommendation

**Do NOT rewrite EraDev. Add a Universal Wrapper layer.**

Architecture:
```
Layer 0 (IMMUTABLE): ODTOE math, 5-role structure, RT protocol, BL budget
Layer 1 (role archetypes, EN/RU): universal role definitions (Direction/Decomposer/Executor/Verifier/Synthesizer)
Layer 2 (domain skins): projects/{domain}/role_skin.md — software terms, article terms, book terms
Layer 3 (project instance): projects/{name}/config.md + lessons.md (today's structure, unchanged)
```

The Universal Wrapper pattern is borrowed from the AgentOrchestra paper (2026): "planning layer remains domain-agnostic, while sub-agents can be expanded." EraDev's META layer is already the planning layer. The 5 roles become a skin-able base class. Domain expertise is injected at role_skin.md read time, via the same Read-then-execute pattern the framework already uses.

## Risks

### Risk 1: HIGH — Epistemic collapse via premature abstraction
Abstracting too early kills domain fidelity. Software-engineering vocabulary carries THOUSANDS of lessons compressed into words like "refactor" and "regression test." Stripping these loses signal.

**Blast Radius**: Framework quality across all domains drops. Users abandon EraDev for CrewAI/AutoGen which remain explicit.

**Mitigation**: Universal layer must be a STRICT SUPERSET, not a REPLACEMENT. Software stack keeps all current vocabulary; new domains get their own vocabularies. Convergence points are the ODTOE math + RT protocol only.

### Risk 2: HIGH — Competition from domain-specialized frameworks
PaperOrchestra (2026) is a dedicated scientific-writing framework with published 84% acceptance rate. Book-Agent, Squibler, and ai-book-writer are mature book-writing frameworks. EraDev universal may lose to specialized tools on any given domain.

**Blast Radius**: EraDev becomes "jack of all trades, master of none" — cost of universality > benefit vs specialized tools.

**Mitigation**: Position EraDev not as a domain tool but as a META-FRAMEWORK. PaperOrchestra SOLVES scientific writing. EraDev ORCHESTRATES arbitrary multi-role work with ODTOE coherence math. The value is in the coherence metrics and self-application loop, not in domain-specific outputs.

### Risk 3: MEDIUM — Bilingual tax doubles for each new domain
Every new domain skin must be written in both EN and RU per BL-19. 4 domains (software / article / book / business) x 2 languages = 8 skin files. Maintenance cost scales linearly.

**Blast Radius**: Sync audit failures pile up; BL-19 violations become the norm; framework integrity decays.

**Mitigation**: Tool the sync audit. Add a bilingual-sync-check.sh Validator Bash (operational) that diff-structures EN and RU skin pairs. Run in CI-equivalent on every commit to domain skins.

### Risk 4: MEDIUM — RT-1 cycle time scales badly for book-length work
Round Table on a single commit is fast. Round Table on a 300-page book chapter with 5 agents each reading a 10-page draft may take 30+ minutes per RT cycle, 3 RT cycles = 90 minutes per chapter.

**Blast Radius**: Book writing with EraDev becomes impractically slow. Operators bypass RT and go solo Builder.

**Mitigation**: Chapter-size = one commit (BL-24 already exists: ">5 files from different modules = RT-2 required"). Introduce a book-specific variant: "chapter = one phase, section = one commit." Also: permit per-domain RT compression modes (RT-Lite for rapid prototyping, RT-Full for integration commits).

### Risk 5: LOW — META-Orchestrator itself becomes domain-unaware
If META is truly universal, it cannot tell the difference between "deploy to prod" and "publish a paper." It may apply the wrong class of constraints.

**Blast Radius**: Meta-level category errors. E.g., running Zero-Downtime checks on a draft article.

**Mitigation**: Task classification step (S/M/L/XL) extends to include DOMAIN detection. Detection signals: file extensions (.md vs .py vs .tex), project config's `domain:` field, keyword analysis on user request. META loads the correct domain skin based on detection.

## True North Alignment Audit

> "EraDev is a self-improving multi-agent framework that applies its own principles to its own development."

**Question 1: Does universalization serve True North?**
YES — universalization is the ultimate self-application test. If EraDev cannot improve its own scope, it cannot claim to self-improve in general. The very act of universalizing IS EraDev applying itself to a new kind of problem (scope expansion), through its own RT cycles. If the RT-1 we are running right now produces a coherent universal architecture, that IS the proof-of-work.

**Question 2: Does universalization break coherence?**
RISK: yes, if done wrong (FM-1, FM-4, Risk 1). But the ARCHITECTURE proposal (Universal Wrapper as opt-in superset) preserves software coherence while adding optional layers. Software users see no change. Universal users get new capabilities. This is additive, not subtractive.

**Question 3: Is the framework itself still "multi-agent" in a meaningful sense after universalization?**
YES. The 5 roles remain. The Round Table remains. ODTOE math remains. Only the vocabulary gains a second, third, fourth skin. This is BL-19 (bilingual architecture) generalized from EN/RU to {EN,RU} x {software,article,book,...}. The bilingual architecture proved that language-as-operator is a feature. Domain-as-operator is the same pattern at the semantic level.

**Question 4: What is the SMALLEST change that preserves the current framework while enabling universality?**
Three files:
1. templates/CLAUDE.md.universal (new bootstrap)
2. roles/archetype/*.md x5 (new abstract role files) + RU pairs
3. projects/{domain}/role_skin.md + BL_tags.md per domain

No eradev.md changes. No meta.md changes. No invariant changes. Minimum viable universality.

## Synthesis for Coherencer

The VISIONARY output for RT-1 converges on a single proposal with three concrete artifacts:

**Proposal**: "Universal Wrapper" pattern — add a role archetype layer UNDER current role files, add domain skin layer OVER them, leave ODTOE core UNTOUCHED. Opt-in via CLAUDE.md.universal template.

**Trade-off**: adds ~5-8 new files, but ZERO changes to existing framework invariants. Adoption cost for software-only users = zero (they keep current CLAUDE.md.software).

**Empirical anchor**: Two independent converged-to-5-roles datapoints (MetaGPT for software, PaperOrchestra for science). n=5 is a stable attractor of the cognitive-work task space.

**Fallback if universalization fails**: Keep EraDev software-only. Publish ODTOE math as the portable contribution. Other frameworks (PaperOrchestra for science, Book-Agent for books) handle their domains; EraDev stays in its lane. This fallback is acceptable because ODTOE math is already the unique contribution; the 5 roles are a reusable pattern but not irreducibly tied to universality.

**Critical question for the team**: Is it better to be the best software multi-agent framework or the second-best universal multi-agent framework? This is a True North question for the Coherencer to arbitrate during RT-1 synthesis.
