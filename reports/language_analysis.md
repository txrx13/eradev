## 2. ПРОБЛЕМЫ ТЕКУЩЕГО СМЕШЕНИЯ

### 2.1. Терминологическое раздвоение
- eradev.md: "Coherent" → glossary.md: "Когерент" → coherent.md: "Когерент (Coherent Agent)"
- eradev.md: "Cognitive Coherence" → glossary.md: "когнитивная когерентность"
- meta.md: "IFR" → visionary.md: "ИКР"
- Один термин — три формы. Для LLM каждая — отдельный токен с отдельными ассоциациями.

### 2.2. Когнитивное переключение агентов
Агент загружает eradev.md (EN) + builder.md (RU) в один контекст. Переключение языкового контекста снижает F (фокус) и повышает sigma (внутренняя противоречивость). По формуле B = F * E * (1-sigma) * Lambda — оба эффекта снижают когерентность.

### 2.3. Токеновая неэффективность
Русский текст потребляет в 1.5–2.5x больше токенов чем эквивалентный английский (кириллица кодируется менее эффективно в BPE-токенизаторах). При загрузке ядро + роль + память + чеклист — русскоязычная часть занимает непропорционально большую долю контекстного окна.

### 2.4. Рекурсивное противоречие
Фреймворк сам определяет Mura как "терминологический разнобой, стилистическое смешение RU/EN" — но сам является примером этого явления. Инструмент валидации не проходит собственную валидацию.

### 2.5. Фантомная декогеренция
При вычислении S_team расхождение |Bi-Bj| между агентами может быть артефактом терминологической путаницы (Визионер использует русские термины из glossary.md, Строитель — английские из eradev.md), а не реальным расхождением в понимании задачи. Языковой шум маскируется под содержательное разногласие.

## 3. КОНСЕНСУС ПЯТИ РОЛЕЙ

### На каком языке LLM работают точнее?

**Все 5 ролей единогласны: английский обеспечивает более точное следование структурированным инструкциям.**

Причины:
1. **Корпус обучения:** 60–90% обучающих данных LLM — на английском. Бенчмарки (MMLU, MGSM, XCOPA) показывают разрыв 5–15% в пользу EN
2. **Токенизация:** английское слово = 1–2 токена, русское = 3–5 токенов. Больше информации на токен = больше инструкций в контекстном окне
3. **Императивные конструкции:** "MUST", "NEVER", "BEFORE generating output" имеют более сильный эффект — модели видели их миллионы раз в системных промптах
4. **Однородность с кодом:** все имена переменных, команды, конфиги — на английском. Промпт на том же языке устраняет "трансляционный мост"

### Нужен ли DSL (Domain-Specific Language)?

**Все 5 ролей: полноценный DSL — нет. Формализованная нотация — да.**

EraDev уже создал де-факто метаязык:
- Математический слой: `B = F * E * (1-sigma) * Lambda`
- TPS-термины: Jidoka, Andon, Hansei, Yokoten (японские, интернационализированные)
- Процессные термины: Round Table, Kill-Switch, True North, Blast Radius
- Операторы: `A_hat = A_Lambda . A_sigma . A_E . A_F`

Этот слой не нужно переводить или заменять — его нужно **стандартизировать** (единая каноническая форма в glossary.md).

### Нужен ли новый язык?

**Нет — но нужна кодификация существующего гибридного языка:**

```
Уровень 1 (инвариантный):  B, S, P_coll, Phi, O_hat — математическая нотация
Уровень 2 (терминологический): Jidoka, Andon, Round Table — имена собственные
Уровень 3 (операционный):  [RT-2][Coherent][S=0.68<0.7] TRIGGER: Kill-Switch L1
```

Уровень 3 — это фактически метаязык EraDev для межагентной коммуникации. Он уже существует, его нужно формализовать.

## 4. РЕКОМЕНДАЦИЯ: ЯЗЫКОВАЯ АРХИТЕКТУРА EraDev

### Модель: "Английское ядро + локализуемый пользовательский слой"

| Слой | Что включает | Язык | Обоснование |
|------|-------------|------|-------------|
| **Ядро** | eradev.md, meta.md, все роли, glossary, checklist | **Английский** | Читается LLM при каждом запуске. Должно быть максимально эффективно |
| **DSL-термины** | B, S, Jidoka, Andon, Round Table, Kill-Switch, True North | **Не переводятся** | Как "git commit" или "pull request" — имена собственные |
| **README** | Входная точка для человека | **Два варианта:** README.md (EN) + README.ru.md (RU) | Стандартная практика open-source |
| **Проекты** | projects/{name}/ | **Язык команды** | Русский для внутренних, английский для международных |
| **Отчёты RT** | A3-шаблоны, spiral_log | **Язык пользователя** | Операционные артефакты, не часть ядра |

### Что даёт переход:
- **Устранение Mura** — единый язык во всём ядре
- **Экономия токенов** — на 30–40% меньше при загрузке контекста
- **Масштабируемость** — open-source, международные команды
- **Точность агентов** — нет переключения языкового контекста
- **Самосогласованность** — фреймворк проходит собственную валидацию на Mura

### Что НЕ теряется:
- Семантика ODTOE сохраняется через glossary.md (двуязычный)
- Русскоязычные пользователи получают README.ru.md
- Проектные файлы могут быть на русском
- TPS-термины и формулы остаются без изменений

## 6. ОЦЕНКА ВЛИЯНИЯ

По формуле D(eta) = D0 * (1-S), текущее языковое расщепление вносит Delta_S ≈ 0.05–0.10 (оценка Когерента). Это превышает допустимый спиральный зазор (pi-3)^2 ≈ 0.02 в 2.5–5 раз.

Устранение языковой Mura — **самый дешёвый способ повысить S_team**: не нужно улучшать качество каждого агента (сложно), нужно убрать искусственные расхождения между ними (просто).
