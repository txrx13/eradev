# RT-2 Coherent: Аналитический отчёт по eradev_old/

**Роль**: Когерент (Round Table, команда 2)
**Дата**: 2026-04-02
**Scope**: Все 7 файлов eradev_old/ (eradev.md, meta.md, analyst.md, builder.md, coherent.md, validator.md, visionary.md)

---

## 1. Связность файлов между собой

Система из семи файлов образует целостную, но асимметричную архитектуру. Центральный узел -- eradev.md -- выполняет роль оркестратора: он определяет теоретический фундамент (ODTOE, TPS, формула когерентности B = F x E x (1-sigma) x Lambda), задаёт процесс (Round Table RT-1/RT-2/RT-3), описывает три зоны сессии (Push/Pull/Resonance) и устанавливает общие протоколы (Bottleneck Expansion, Kill-Switch, Nemawashi, Pull-якорь, Prediction Delta). Пять ролевых файлов (analyst.md, builder.md, coherent.md, validator.md, visionary.md) функционируют как специализированные инстансы этой общей рамки, а meta.md замыкает контур обратной связи, наблюдая за всеми остальными.

Связность между ролевыми файлами реализована через несколько механизмов. Во-первых, каждый файл явно указывает входные и выходные данные, формируя цепочку зависимостей: Визионер задаёт стратегию и приоритеты, Аналитик проектирует план, Строитель реализует, Валидатор проверяет, Когерент синхронизирует. Во-вторых, все пять ролей содержат одинаковый блок "Андон" -- общий протокол остановки при обнаружении проблемы. В-третьих, файлы перекрёстно ссылаются на общие артефакты: docs/ROADMAP.md, MEMORY.md, docs/CONTRIBUTING.md, docs/ARCHITECTURE.md. Наконец, meta.md содержит спиральную память (Витки 1-4), в которой каждый инцидент привязан к конкретным агентам через B-дефициты (F, E, sigma, Lambda).

Однако связность неравномерна. Builder.md и validator.md связаны наиболее тесно -- чеклисты Валидатора прямо адресуют выходы Строителя (Go build, pnpm build, Security Checklist, feature flags). Visionary.md, напротив, наименее связан с остальными: он содержит всего 3 урока от Meta-Agent против 9 у Строителя и 16 у Валидатора. Analyst.md занимает промежуточное положение -- он порождает планы, которые потребляют и Строитель, и Валидатор, но сам получает входные данные преимущественно от Визионера. Coherent.md оказывается связующим узлом второго порядка -- он документирует решения всех остальных, но не влияет на технические решения напрямую.

## 2. Единый стиль и терминология

В системе присутствует ядро общей терминологии, которое корректно воспроизводится во всех файлах: Round Table (RT-1/RT-2/RT-3), Андон, Jidoka, Hansei, True North, ИКР (Идеальный Конечный Результат), B-формула (F, E, sigma, Lambda), blast radius, feature flags, rolling deploy. Эта терминология пришла из двух источников -- Toyota Production System и ODTOE -- и стабильно прошита через все семь файлов.

Стилистически файлы выдерживают единый формат: заголовок "Роль", "Твой главный вопрос", "Обязанности", "Как ты работаешь", "Входные/Выходные данные", "Принципы", "Антипаттерны", затем уроки от Meta-Agent с нумерацией вида "Паттерн PN: описание" и "Правило XN.M". Этот формат создаёт предсказуемость -- агент (или человек), читающий любой ролевой файл, сразу ориентируется в структуре.

При этом терминологическая неоднородность проявляется в нескольких зонах. Первое: японские термины (Muda/Mura/Muri, Jidoka, Hansei, Yokoten, Nemawashi, Andon) определены в eradev.md, но в ролевых файлах используются без повторного определения -- в coherent.md "Kill-Switch / Аттракторный мониторинг", в validator.md "Шкала управляемого диссонанса", в analyst.md "Muri-детектор". Это создаёт ситуацию, когда агент, читающий только свой ролевой файл, может не понять связь между "Kill-Switch" в своём файле и "Jidoka Self-Check" в eradev.md. Второе: смешение русского и английского языков неравномерно -- builder.md содержит значительно больше англоязычных блоков (Security Checklist, Decision-Point Checklist), тогда как visionary.md почти полностью на русском. Meta.md переходит на английский в формулах и категориях инцидентов (категории A-R). Третье: нумерация уроков Meta-Agent использует разные префиксы (A для Аналитика, B для Строителя, C для Когерента, V для Валидатора, Vi для Визионера), что логично, но вперемешку с "Паттерн P1, P2..." в meta.md и "MP5, MP6..." для мега-паттернов это создаёт когнитивную нагрузку при навигации.

## 3. Ядро vs специфика проекта

Чёткое разделение ядра и проектной специфики -- это главная структурная проблема текущей версии системы. Ядро EraDev (универсальные принципы мультиагентной разработки) и специфика проекта EraWeb3/Academic Lab (конкретные технологии, API, инфраструктура) переплетены внутри каждого файла, а не разделены между файлами.

**Ядро** (то, что переносимо на любой проект):
- Пять ролей и их взаимодействие (оркестрация через Round Table)
- Формула когерентности B = F x E x (1-sigma) x Lambda
- Процесс RT-1/RT-2/RT-3
- Протоколы: Андон, Bottleneck Expansion (ТОС + ТРИЗ + СМД), Kill-Switch, Nemawashi
- TPS-механизмы: Muda/Mura/Muri, Jidoka Self-Check, Hansei, Yokoten
- A3-шаблон кристаллизации
- Prediction Delta Tracking
- Session Architecture (Push/Pull/Resonance)
- Спиральная память как концепция
- Meta-Agent как контур самомодификации
- Мета-мета-правила (MM1-MM5)
- Мега-паттерны (MP1-MP8) -- на уровне абстрактных формулировок

**Специфика проекта EraWeb3** (непереносимо):
- Конкретные технологии: Go (eradns, eraweb), TypeScript/Next.js, Bash (autodeploy.sh)
- Конкретные команды сборки: GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build, pnpm build
- Конкретные порты: 53, 80, 443, 3000, 8053, 9057
- Конкретная инфраструктура: 7 нод, Москва-специфика, autodeploy.sh каждую минуту
- Erachain blockchain API: типы транзакций, Base64 broadcast, RIPEMD160, Note version 2
- Конкретные файлы: app/blockchain/persons/[key]/page.tsx, scripts/autodeploy.sh
- Спиральная память Витков 1-4 -- это артефакт конкретного проекта
- Security Checklist в builder.md: конкретные TLS/HTTP/network правила для данного проекта
- Decision Log в coherent.md: конкретные решения проекта Academic Lab
- Реестр инцидентов (категории A-R) в meta.md

Проблема в том, что эти два слоя размешаны. Например, в builder.md "Правило B10.1" начинается с универсального принципа ("Перед написанием компонента для blockchain данных -- сделай curl к реальному API"), но затем переходит к специфике ("person/1, person/1052, string birthday, null balances"). Аналогично, analyst.md содержит универсальное правило A6.2 ("Каждый план должен покрывать ПОЛНЫЙ pipeline"), но иллюстрирует его проектно-специфичным примером (Next.js, npm run build). В meta.md спиральная память -- это одновременно и метод (универсальный) и содержание (специфичное для EraWeb3).

## 4. Диспропорции объёмов и глубины

Объёмы файлов крайне неравномерны: meta.md (815 строк) и eradev.md (1063 строки) вместе составляют более 75% всего текста системы. Builder.md (223 строки) и validator.md (303 строки) представляют средний эшелон. Visionary.md (68 строк) -- минимален, что создаёт Mura (неравномерность). Визионер формально отвечает за стратегию и архитектуру, но его файл содержит лишь 3 урока от Meta-Agent, тогда как Строитель -- 19, Валидатор -- 16. Это отражает реальность проекта (большинство инцидентов -- технические), но обедняет стратегическую роль.

Coherent.md (157 строк) содержит Decision Log и instability watchlist, что делает его наиболее "привязанным" к конкретному проекту среди ролевых файлов. При переносе на другой проект этот файл потребует наибольшей переработки -- не потому что его структура плоха, а потому что его содержание на 60% состоит из проектной специфики.

## 5. Аттракторные риски и структурные противоречия

В системе обнаруживается несколько структурных напряжений. Первое: meta.md разрастается линейно (Виток 1 + Виток 2 + Виток 3 + Виток 4 = 815 строк), что сам meta.md диагностирует как проблему ("Промпт растёт >200 строк = перегрузка правилами. Сжать, обобщить, удалить дубли."), но не решает. Каждый виток добавляет новые категории инцидентов, мега-паттерны и мета-правила, не сжимая предыдущие. К Витку 8-10 meta.md станет нечитаемым.

Второе: между Витками наблюдается паттерн "правила накапливаются, но Lambda = 0 не уменьшается". Виток 4 явно фиксирует это: "Знание без enforcement = знание без эффекта." Это фундаментальный вопрос -- если агент (AI или человек) не применяет правила из 700+ строк промпта, проблема не в качестве правил, а в архитектуре их доставки.

Третье: между eradev.md (универсальный оркестратор) и ролевыми файлами (специализированные) существует дублирование. Jidoka Self-Check описан и в eradev.md, и в builder.md. Kill-Switch/Шкала диссонанса -- в eradev.md, validator.md, coherent.md. Mura/Muri-детекторы -- в eradev.md, analyst.md, validator.md. Это нарушает принцип DRY и создаёт риск рассинхрона при редактировании.

## 6. Рекомендации для универсальной версии

**6.1. Разделить ядро и проектную специфику на уровне файлов.**
Предлагаемая структура:
- `eradev/core/` -- ядро (eradev.md, 5 ролевых файлов, meta.md) без единой проектной ссылки
- `eradev/memories/{project}.md` -- проектная специфика (уже предусмотрено, но не реализовано полностью)
- Ролевые файлы в core/ содержат только универсальные принципы; проектные чеклисты, команды сборки, порты, технологии -- в memories/

**6.2. Ввести иерархию правил с явными уровнями.**
Текущая плоская структура (все правила на одном уровне) не масштабируется. Предлагается три уровня:
- Уровень 1 (железные, 5-7 правил): "Прочитай перед изменением", "Проверь build перед push", "Андон при проблеме", "Blast radius определяет строгость", "Факты перед кодом"
- Уровень 2 (доменные, 10-15 правил per role): специфичные для домена (frontend, infra, crypto), загружаются по контексту задачи
- Уровень 3 (проектные, N правил): конкретные для данного проекта, хранятся в memories/

**6.3. Сжать meta.md через кристаллизацию витков.**
Вместо линейного наращивания (Виток 1 + Виток 2 + ...) -- хранить только: (а) текущие действующие правила (Result), (б) последний виток полностью (Context), (в) сжатый индекс предыдущих витков (Reference). Старые витки архивировать в отдельные файлы. Это снижает нагрузку на контекстное окно агента.

**6.4. Устранить дублирование через ссылки.**
Jidoka Self-Check, Kill-Switch, Mura/Muri-детекторы должны быть определены ОДИН раз в eradev.md, а в ролевых файлах -- только ссылка ("Применяй Jidoka Self-Check из eradev.md после каждого блока работы"). Это предотвратит рассинхрон и уменьшит объём ролевых файлов.

**6.5. Усилить visionary.md.**
68 строк для стратегической роли недостаточно. Визионер должен содержать: (а) чеклист оценки blast radius для новых задач (сейчас в coherent.md), (б) протокол Zone Detection с примерами (сейчас кратко), (в) собственные уроки о стратегических ошибках (не только 3 абстрактных правила). Баланс объёмов между ролями важен для когерентности команды -- если Визионер "легковесен", его голос теряется в Round Table.

**6.6. Стандартизировать языковую политику.**
Принять явное решение: либо русский как основной с англоязычными терминами и кодом, либо английский полностью. Текущее ad hoc смешение ("Security Checklist (ОБЯЗАТЕЛЬНО перед завершением)", "Threat modeling: for every new feature") создаёт когнитивный переключатель. Для универсальной версии (если она предполагает международное использование) рекомендуется английский; для внутреннего использования -- русский с устойчивым глоссарием заимствований.

**6.7. Формализовать enforcement-механизмы в отдельном файле.**
Виток 4 выявил Lambda-gap: правила существуют, но не применяются. Решение -- отдельный файл `eradev/enforcement.md` или секция в eradev.md с конкретными автоматизируемыми проверками: pre-push hooks, обязательные чеклисты на decision points (feature flag activation, protocol change, git push). Этот файл должен содержать не "что проверять" (это в ролевых файлах), а "как гарантировать что проверка произойдёт".

## Итоговая оценка когерентности системы

Система eradev_old/ демонстрирует высокую внутреннюю связность на уровне концепций и среднюю -- на уровне реализации. Теоретический фундамент (ODTOE + TPS) последовательно прошит через все файлы. Процессная рамка (Round Table, A3, Prediction Delta) логична и работоспособна. Спиральная память Meta-Agent показывает реальное обучение системы (fix rate снизился с 67% до 40% после введения EraDev). Главные точки роста для универсальной версии: разделение ядра и проектной специфики, сжатие линейно растущего meta.md, устранение дублирования, балансировка объёмов между ролями и формализация enforcement-механизмов.

S_team текущей конфигурации (по субъективной оценке из роли Когерента): ~0.72. Потери: Mura (неравномерность объёмов и глубины ролей), Muri (перегрузка builder.md и meta.md), Muda (дублирование протоколов между файлами, устаревшие проектные детали в ядре). При реализации рекомендаций 6.1-6.7 прогнозируемый S_team: ~0.88.
