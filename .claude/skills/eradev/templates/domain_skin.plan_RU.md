## Назначение / Когда META загружает этот скин

META загружает этот скин, когда `config.md` проекта объявляет:
- `domain.type: plan`
- `domain.skin: templates/domain_skin.plan.md`

При загрузке скин передаётся каждому порождённому ролевому агенту дополнительно к базовому файлу роли `roles/{role}_EN.md`. Он НЕ заменяет файл роли — предоставляет маппинг словаря, переопределения фокуса, расширение верификации, корректировки RT, примеры и таблицу наследуемых/переопределённых BL, специфичную для работы по составлению планов. Скин нацелен на дорожные карты, фазированные планы выполнения и структурированные процедуры, корректность которых измеряется тем, может ли читатель-не-автор пройти их шаг за шагом. Ранбуки, SOP, плейбуки инцидентов и чеклисты онбординга — смежные классы, которые МОГУТ использовать этот скин как есть до написания более специфичного.

Домен plan разделяет модальность `text` с `code` (равномерные веса 0.25), но расходится по верификации: code использует `build` (компиляция+тесты+линтер), plan использует `dry_run` (мысленное выполнение плана читателем-не-автором). Это нагрузочный новый метод верификации, который скин привносит.

## Модальная B-формула (text-веса, равномерные 0.25×4)

Этот скин пинит `B_modality: text`. Builder / Validator / Coherent для планов используют text (равномерные) веса:

| Компонент | Вес | Обоснование |
|---|---|---|
| F (Фокус) | **0.25** | Авторы должны были прочитать предыдущее состояние и охватывающий контекст — предыдущие фазы roadmap, существующие планы для той же цели, проектный глоссарий. |
| E (Выравнивание) | **0.25** | План должен решать реальную цель оператора — не «хорошо читающийся план», а «план, чьё завершение удовлетворяет исходный запрос». |
| (1-σ) (Согласованность) | **0.25** | Фазы не должны противоречить друг другу (один ресурс назначен на два параллельных потока = конфликт; две фазы с висячими пререквизитами друг на друга = дедлок). |
| Λ (Опыт) | **0.25** | Постмортемы предыдущих планов (выходы Hansei) должны информировать этот план — BL-12 для планов. |

**Почему `text`, а не `creative` или `research` (ЗАКРЕПЛЕНО — БЕЗ переопределения):**
1. Ни один компонент не доминирует в составлении планов — все четыре важны примерно одинаково.
2. Планы — текстовые артефакты, не теорема/доказательство. Нет цепочки доказательств для фальсификации.
3. Планы — НЕ творческая длинная проза. Голос и соответствие читателю важны менее, чем ВЫПОЛНИМОСТЬ плана.

## Переопределения фокуса ролей

Каждая роль сохраняет свой Оператор Активации (A_F, A_E, A_σ, A_Λ) и Jidoka-самопроверку из `roles/{role}_EN.md` **без изменений**. Скин добавляет ДОМЕННО-СПЕЦИФИЧНЫЕ якори фокуса, определения артефактов, режимы отказов и Jidoka-специализации.

### Visionary (фокус на планах)

- **ПЕРВЫЙ якорь фокуса (переопределение A_F):** Прочитать ОРИГИНАЛЬНЫЙ запрос оператора дословно (не перефразированный). Прочитать любой существующий план для той же или смежной цели (проверка замещения — BL-P3). True North = *что означает «готово» для этой цели, сформулированное в прошедшем времени как измеримый результат?*
- **Определение артефакта:** Центральная цель + её границы. НЕ фазы, НЕ шаги, НЕ DAG зависимостей — это артефакт Analyst.
- **Основной режим отказа:** Одобрение плана с расплывчатой целью или субъективным состоянием «готово».
- **Jidoka-самопроверка:** Q1 «Готово» ИЗМЕРИМО? / Q2 Область ОГРАНИЧЕНА? / Q3 Замещение существующего плана? / Q4 Цель дискретно-фальсифицируема?

### Analyst (фокус на планах)

- **ПЕРВЫЙ якорь фокуса (переопределение A_F):** Прочитать формулировку цели от Visionary. Прочитать предыдущие планы для той же/смежной цели (BL-29). Прочитать охватывающий план (если это подплан). ЗАТЕМ составить декомпозицию по фазам.
- **Определение артефакта:** Структурированный документ плана с РОВНО 9 обязательными частями:
  1. Блок цели (дословно из RT-0 Visionary)
  2. Границы объёма (внутри / вне)
  3. Фазы с именованными длительностями, владельцами, поставками
  4. DAG зависимостей
  5. Критерии прохождения по фазам (измеримые)
  6. Распределение ресурсов
  7. Контингенции
  8. Известные Out-of-Scope
  9. Открытые вопросы / CORS
- **Основной режим отказа:** «Красивый контур» с пробелами — фазы названы, но списки шагов отсутствуют, зависимости не указаны явно, критерии прохождения сведены к вайбам.
- **Jidoka-самопроверка:** Q1 Все 9 частей? / Q2 Владельцы поименованы? / Q3 Входы обеспечены? / Q4 Критерии ИЗМЕРИМЫ? / Q5 Длительности сходятся к итогу?

### Builder (фокус на планах)

- **ПЕРВЫЙ якорь фокуса (переопределение A_F):** Прочитать черновик Analyst дословно. Прочитать живой эталонный артефакт плана как стандарт формата. Прочитать устоявшуюся терминологию проекта (BL-29). НЕ начинать шлифовку прозы до завершения всех трёх чтений.
- **Определение артефакта:** Единый файл документа-плана (`.md`). Артефакт — НЕ набор буллет-пойнтов в чат-треде — это СОХРАНЁННЫЙ ФАЙЛ с каноническим путём и полем версии в заголовке.
- **Основной режим отказа:** Шлифовка прозы до стабилизации структуры.
- **Вторичный режим отказа:** Расширение объёма при шлифовке — BL-11.
- **Третичный режим отказа:** Анонимные владельцы — «команда сделает это».
- **Jidoka-самопроверка:** Q1 Черновик Analyst прочитан полностью? / Q2 Эталонный план прочитан? / Q3 Объём совпадает с черновиком? / Q4 Все владельцы поименованы? / Q5 Терминология точная (BL-29)? / Q6 Markdown рендерится чисто?

### Validator (фокус на планах)

- **ПЕРВЫЙ якорь фокуса (переопределение A_F):** Прочитать план Analyst + шлифованный план Builder. Запустить 6 суб-проверок dry_run из Секции 4 (DR1–DR6). Validator НЕ пропускает ни одну.
- **Определение артефакта:** Шлифованный файл плана В ФИНАЛЬНОМ ВИДЕ — то, что прочитает команда исполнения утром первого дня.
- **Основной режим отказа:** Запуск только DR1 и объявление PASS, пока план имеет неизмеримые критерии ИЛИ отсутствующие контингенции.
- **Jidoka-самопроверка:** Q1 Все 6 DR запущены? / Q2 Критерии ИЗМЕРИМЫ? / Q3 Контингенции есть? / Q4 Длительности обоснованы? / Q5 Длительности сходятся к итогу? / Q6 Могу ли я начать фазу 0 шаг 1 без вопроса автору?

### Coherent (фокус на планах)

- **ПЕРВЫЙ якорь фокуса (переопределение A_F):** Прочитать полный план от начала до конца, дважды — сверху вниз и снизу вверх. Прочитать `lessons.md` проекта для правил, которые план должен соблюдать (BL-29).
- **Определение артефакта:** План + (все предыдущие планы для той же/смежной цели) = серия планов. Coherent проверяет, что ТЕКУЩИЙ план не противоречит и не дублирует предыдущие.
- **Основной режим отказа:** «Терминологический дрифт между секциями» — ранние фазы говорят «спринт», поздние — «итерация».
- **Вторичный режим отказа:** Фантомная когерентность — все критерии «выглядят строго», но все сводятся к одному субъективному суждению.
- **Jidoka-самопроверка:** Q1 Термины согласованы по фазам? / Q2 Длительности СХОДЯТСЯ? / Q3 Критерии ДЕЙСТВИТЕЛЬНО независимы? / Q4 Противоречие/дублирование с предыдущим планом? / Q5 Спот-чек 3 случайных шагов?
- **Правило замещения (BL-P3):** Coherent — ПРИНУДИТЕЛЬ протокола замещения. Коммит ЗАБЛОКИРОВАН, если предыдущий план не архивирован с маркером «замещён vX».

## Протокол верификации (dry_run расширенный)

Скин расширяет `dry_run` в 6 суб-проверок (DR1–DR6), разделённых на механические (почти автоматизируемые) и интерпретативные (требующие суждения).

### Шесть проверок dry_run

| # | Проверка | Что обнаруживает | Кто запускает | Механизм |
|---|---|---|---|---|
| **DR1** | **Пошаговое прохождение** — мысленно выполнить каждый шаг; шаг должен быть самодостаточным | Нечёткие / невыполнимые шаги; шаги с неявным знанием | Validator | Почти механическая |
| **DR2** | **Проверка пререквизитов** — входы каждого шага обеспечены предыдущим шагом или объявлены как внешние | Висячие пререквизиты; фантомные входы | Validator | Механическая — граф входов шагов |
| **DR3** | **Полнота ресурсов** — каждый актор, инструмент, бюджет и дедлайн поименованы | Анонимные владельцы, отсутствующие инструменты | Validator | Механическая — grep на «мы», «команда», «TBD» |
| **DR4** | **Наличие контингенций** — для каждой фазы: что если фаза не удалась? | Планы только для «счастливого пути» | Validator | Интерпретативная |
| **DR5** | **Измеримость критериев успеха** — «готово» каждой фазы квантифицируемо | Планы с вайб-критериями | Validator | Почти механическая — сканирование критериев |
| **DR6** | **Ясность хендоффов** — каждый переход между фазами имеет явную смену владельца ИЛИ явную пометку «тот же владелец продолжает» | Неявные хендоффы | Coherent | Интерпретативная |

### L1 (механические) vs L2 (интерпретативные)

- **L1 (механические, по-коммитно):** **DR1, DR2, DR3, DR5** — все четыре сводимы к структурным сканам. Запускаются при каждой ревизии плана.
- **L2 (интерпретативные, перед активацией):** **DR4, DR6** — требуют вдумчивого читателя. Запускаются однократно перед объявлением плана ДЕЙСТВУЮЩИМ.

### Аналогия с code-скином `build`

| Проверка code | Аналог plan |
|---|---|
| `compile` (проходит ли типчек?) | DR1 + DR2 (последовательность шагов имеет смысл?) |
| `test` (юнит-тесты проходят?) | DR3 + DR5 (ресурсы названы и критерии измеримы?) |
| `lint` (стилевые нарушения?) | DR6 + BL-29 глоссарий (терминология согласована?) |
| `integration tests` (модули кооперируют?) | DR4 (фазы кооперируют на границах хендоффов?) |

### Блок верификации

```
method:           dry_run
command:          N/A для автоматизации dry_run; план выполняется мысленно читателем
                  (человек или LLM-агент), который не является автором. Механические средства:
                  - Markdown lint: `markdownlint plan.md` (рендерится чисто)
                  - Grep ресурсов: `grep -nE "\b(we|the team|someone|TBD|n/a)\b" plan.md`
                    → ноль хитов = PASS по анонимным владельцам
                  - Проверка суммы длительностей (ручная): сложить длительности фаз, сравнить с итогом
                  - Кросс-фазная терминология (BL-29): извлечь все капитализированные имена фаз/гейтов/ролей
success criteria: все 6 DR PASS (DR1–DR6) И файл плана рендерится чисто как Markdown
                  И все 9 обязательных частей шаблона Analyst присутствуют И проверка
                  замещения (BL-P3) подтверждает отсутствие конфликта с предыдущим планом
failure recovery: DR1 → определить нечёткие шаги, переписать с явными суб-действиями
                  DR2 → добавить шаг, производящий недостающий вход, или объявить внешним
                  DR3 → поименовать владельцев, инструменты, бюджеты, дедлайны
                  DR4 → добавить параграф контингенции для каждой фазы
                  DR5 → заменить субъективный критерий числовым/бинарным
                  DR6 → добавить явную пометку смены владельца на каждой границе фазы
independence check: Validator запускает dry_run БЕЗ участия в авторском разговоре.
                  Фантомная когерентность (BL-5): если Builder и Validator оба говорят PASS,
                  но ни один не прошёл шаги 1→N последовательно — флаг PHANTOM DRY_RUN.
```

## Корректировки протокола RT-фаз

### Три точки вызова RT для планов

1. **RT-0 (Visionary соло, РЕКОМЕНДУЕТСЯ):** захват цели + OOD-проверка.
2. **RT-1 (обязательный, полная пятёрка ролей):** декомпозиция + валидация. Производит шаблон Analyst + шлифованный план Builder + первый проход DR1–DR5 Validator + глоссарий Coherent.
3. **RT-2 (обязательный, перед активацией):** полный dry_run + унификация терминологии. Все 6 DR-проверок + BL-29 глоссарий + BL-P3 замещение.

### Конфигурация Builder — один или разделённый?

**Решение: один Builder, кроме XL.**

Ритм внутри единого Builder:
- Прочитать черновик Analyst
- Прочитать живой эталонный план для выравнивания формата
- Шлифовать секция за секцией (цель → объём → фазы → DAG → критерии → контингенции → OOD → открытые вопросы)
- Внутренняя самопроверка: рендер Markdown, grep анонимных владельцев, сумма длительностей
- Коммит

**Исключение (только XL):** для XL-плана (>10 фаз ИЛИ >2 недели длительности ИЛИ >3 именованных владельца) Analyst МОЖЕТ разделить работу между двумя Builders по владению фазами.

### Пайплайн плана (ФИКСИРОВАННЫЙ)

```
RT-0 (Visionary соло, РЕКОМЕНДУЕТСЯ) → захват цели + OOD + проверка замещения
RT-1 (полная пятёрка) → 9-частный черновик Analyst + шлифовка Builder + DR1–DR5 Validator + глоссарий Coherent
    [опциональный RT-1.5 после каждой крупной группы фаз для XL-планов]
Гейт Coherent (после завершения шлифовки Builder)
RT-2 (полная пятёрка) → 6 DR-проверок + BL-29 глоссарий + BL-P3 замещение
Коммит файла плана + архивирование замещённого предыдущего плана
План становится ДЕЙСТВУЮЩИМ → передаётся команде исполнения → вне области RT
```

## Примеры (3 конкретные задачи)

### Пример 1: Висячий пререквизит (отказ DR2)

- **Вход:** «Составить план миграции бэкенда с Postgres на Cockroach. Включая миграцию схемы, репликацию данных и переключение.»
- **Классификация домена:** type=plan, modality=text, verify=dry_run, blast_radius=HIGH
- **Сценарий:** Analyst составляет 5-фазный план. Фаза 4 (переключение) говорит «задеплоить новый конфиг, маршрутизирующий чтения на Cockroach» — но ни одна предыдущая фаза не производит этот конфиг. Висячий пререквизит.
- **Роль-ловец:** **Validator** (DR2).
- **Фаза:** **RT-1**.
- **Исправление:** Добавить фазу 3.5: «произвести конфиг маршрутизации чтений».
- **B-проверка:** F=0.85, E=0.90, 1-σ=0.85, Λ=0.80 → B ≈ 0.52 ЖЁЛТЫЙ

### Пример 2: Неизмеримый критерий успеха (отказ DR5)

- **Вход:** «Составить план Q2 по улучшению онбординга.»
- **Классификация домена:** type=plan, modality=text, verify=dry_run, blast_radius=MEDIUM
- **Сценарий:** Все 4 критерия фаз субъективны: «когда проинтервьюируем команду», «когда вайрфреймы будут выглядеть чисто», «когда код будет ощущаться хорошо», «когда пользователи будут довольны». DR5 ОТКАЗ с 4/4 неизмеримыми критериями.
- **Роль-ловец:** **Validator** (DR5).
- **Фаза:** **RT-1** (DR5 — L1 механическая, по-коммитная; запускается на RT-1). Но Jidoka Analyst Q4 должен был поймать на RT-1; пропуск — дефект процесса для Hansei.
- **Исправление:** Переписать каждый критерий как измеримый.
- **B-проверка:** F=0.85, E=0.95, 1-σ=0.80, Λ=0.85 → B ≈ 0.55 ЖЁЛТЫЙ

### Пример 3: Терминологический дрифт между фазами (σ-отказ Coherent)

- **Вход:** «Составить план релизного цикла Q2 2026, включая планирование спринтов, ревью итераций, ретроспективы и дату отгрузки.»
- **Классификация домена:** type=plan, modality=text, verify=dry_run, blast_radius=MEDIUM
- **Сценарий:** Фазы 0-2 используют «спринт» последовательно. Фазы 3-5 дрифтуют к «итерация». Фаза 6 смешивает оба: «Финальный ревью итерации спринта». Coherent строит мини-глоссарий: «спринт» 14 раз, «итерация» 11 раз. Тихое противоречие.
- **Роль-ловец:** **Coherent** (BL-29 для планов).
- **Фаза:** **RT-2**.
- **Исправление:** Унифицировать: заменить «итерация» на «спринт» по всем фазам 3-5, разрешить фазу 6.
- **B-проверка:** F=0.85, E=0.80, 1-σ=0.70, Λ=0.85 → B ≈ 0.41 КРАСНЫЙ

## Известные Out-of-Scope (OOD)

- **Непрерывные / потоковые цели.** «Улучшить моральный дух команды» — нет дискретного критерия. ОТКАЗ по `verify.method`.
- **Субъективные цели.** «Сделать продукт лучше по ощущениям» — эстетическое суждение непрерывно. ОТКАЗ.
- **Непрерывная настройка работающей системы.** Ops-ручки, real-time пороги — потоковые корректировки, не text-discrete планы. OOD для v9.
- **Вербальные / культурные ритуалы.** «Спланировать вайб квартального оффсайта» — нет DR3/DR5 структуры. OOD для v9.
- **Культурные дорожные карты / раскатки ценностей.** Нагрузочное свойство — скорость адаптации, которая непрерывна. Отложено до v10.
- **Исследовательские дорожные карты (теорема / доказательство).** Маршрутизировать на скин `research`.
