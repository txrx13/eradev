# Доменный скин: book

> Тип: book
> Модальность: creative
> OOD-область: text-discrete
> Применяется к проектам с `config.md` содержащим `domain.type: book`
> Родительские BL: BOOTSTRAP_LESSONS_universal.md (22 универсальных BL наследуется)
> НЕ наследует BOOTSTRAP_LESSONS_code_adapter.md
> Метод верификации: readability (первичный) + structural coherence (вторичный)
> Двуязычность: опционально для проекта (BL-19 условный)
> Вышестоящие роли: roles/{role}_EN.md
> Вышестоящая математика: eradev.md Section II.1 (веса B_creative)
> Последнее обновление: 2026-04-11

---

## Назначение / Когда META загружает этот скин

META загружает этот скин, когда `config.md` проекта объявляет `domain.type: book` и `domain.skin: templates/domain_skin.book.md`. Скин передаётся каждому ролевому агенту дополнительно к `roles/{role}_EN.md`. Он НЕ заменяет файл роли. Скин нацелен на учебники, академические монографии и нехудожественную длинную форму (how-to, история, поп-наука) — НЕ романы, НЕ поэзию, НЕ чисто-личные мемуары. См. «Known Out-of-Scope» ниже.

Обратная совместимость: введение этого скина НЕ требует изменений в существующих проектах.

## Модальная B-формула (creative-веса)

| Компонент | Вес | Обоснование |
|---|---|---|
| F (Фокус) | **0.20** | Фоновое чтение + скан эталонных книг важны, но книга может частично стоять на собственном авторитете. |
| E (Выравнивание) | **0.30** | **Доминантный (в паре с 1-σ).** Книга должна доставить обещание контура / задней обложки / предисловия. |
| (1-σ) (Согласованность) | **0.30** | **Доминантный (в паре с E).** Кросс-главная терминология, утверждения и непрерывность концептов — доминантный режим отказа. |
| Λ (Опыт) | **0.20** | Память проекта книги накапливается медленно; Λ — фасилитатор, не гейт. |

## Переопределения фокуса ролей

### Visionary (фокус на книгах)
- **ПЕРВЫЙ якорь:** Прочитать центральное утверждение и профиль целевого читателя. Прочитать скетч 3-главной арки. True North = *какое изменение эта книга производит в мышлении читателя?*
- **Основной режим отказа:** «Жанровая коллизия» — одобрение тезиса, уже хорошо покрытого существующими книгами.
- **Вторичный:** Тезис слишком велик для книги (30+ глав).
- **Jidoka:** Q1 тезис дифференцирован? / Q2 фальсифицируем? / Q3 3-главная арка доставляет? / Q4 бюджет читательского времени оборонителен?

### Analyst (фокус на книгах)
- **ПЕРВЫЙ якорь:** Прочитать контур (части → главы → секции), глоссарий, граф зависимостей по главам. Затем прочитать профиль целевого читателя. НЕ продолжать декомпозицию до завершения триады контур-глоссарий-зависимости.
- **Определение артефакта:** Таблица декомпозиции по главам: утверждения, термины, зависимости, бюджет длины. ТАБЛИЦА, не проза.
- **Основной режим отказа:** Пропуск графа зависимостей.
- **Вторичный:** Недооценка глоссария.
- **Jidoka:** Q1 триада прочитана? / Q2 зависимости явные? / Q3 бюджеты длины? / Q4 глоссарий покрывает кросс-главные термины? / Q5 стратегия rolling update?

### Builder (фокус на книгах)
- **ПЕРВЫЙ якорь:** Прочитать план Analyst дословно. Прочитать стайл-гайд + 1-2 эталонные книги жанра. Прочитать предыдущие главы (BL-29). НЕ начинать прозу до завершения трёх чтений.
- **Определение артефакта:** Одна глава за раз, в полной длине как единый адресуемый юнит.
- **Основной режим отказа:** Черновик без проверки обратной согласованности с предыдущими главами.
- **Вторичный:** Дрифт от контура.
- **Третичный:** Дрифт бюджета длины (2-3× сверх бюджета).
- **Четвёртый:** Глоссарный дрифт ВНУТРИ одной сессии Builder.
- **Jidoka:** Q1 план + стайл-гайд + эталоны прочитаны (F)? / Q2 глава доставляет обещание контура (E)? / Q3 grep предыдущих глав на каждый ключевой термин (1-σ)? / Q4 длина ±20% бюджета? / Q5 глоссарий перечитан в начале сессии (Λ)? / Q6 для двуязычных: парная глава тоже написана (BL-19)?

### Validator (фокус на книгах)
- **ПЕРВЫЙ якорь:** Прочитать ВСЮ рукопись (все написанные главы) + контур Analyst + глоссарий. НЕ валидировать частично.
- **Основной режим отказа:** Проверка только по-главных свойств и пропуск кросс-главной непрерывности.
- **Вторичный:** Доверие скомпилированному PDF — «выглядит как книга» → PASS.
- **Третичный:** Пропуск нарушений бюджета длины.
- **Jidoka:** Q1 все 6 R запущены? / Q2 R1 (Flesch) числовой? / Q3 R2 кросс-главный скан противоречий? / Q4 R3 (глоссарий) проверен? / Q5 R4 (верность контуру) + длинный реестр? / Q6 R6 (целевой читатель)? / Q7 (двуязычный): обе версии?

### Coherent (фокус на книгах)
- **ПЕРВЫЙ якорь:** Прочитать полную рукопись + глоссарий + контур. Coherent заботится о *внутренней когерентности рукописи*.
- **Основной режим отказа:** **Глоссарный дрифт** — ключевой термин используется с разными значениями в разных главах (BL-29). См. Пример 1.
- **Вторичный:** Инвалидация кросс-главных ссылок.
- **Третичный:** Фантомная когерентность внутри рукописи (BL-5).
- **Jidoka:** Q1 каждый термин глоссария по каждой главе (BL-29)? / Q2 «как мы установили в Гл.N» ссылки не устарели? / Q3 тихие коллизии символов? / Q4 RU и EN параллельны (BL-19 условный)? / Q5 независимый спот-чек 2 утверждений?
- **Правило Yokoten (BL-13 + BL-32):** При обновлении глоссарного термина — grep всей рукописи на СТАРЫЙ термин и обновить каждое вхождение в ТОЙ ЖЕ ревизии.
- **Двуязычная синхронизация (BL-19 условный):** Если проект объявляет `domain.bilingual: true`, Coherent — ПРИНУДИТЕЛЬ парного языка. Коммит ЗАБЛОКИРОВАН при отсутствующей парной версии. Если проект НЕ объявляет `domain.bilingual: true` — правило НЕАКТИВНО.

## Протокол верификации (readability + структурная когерентность)

### Шесть R-проверок

| # | Проверка | Кто | L1/L2 | Механизм |
|---|---|---|---|---|
| **R1** | **Читаемость (Flesch-Kincaid)** — средний балл по книге в целевой полосе; по-главная дисперсия ≤4 уровня | Validator | **L1/L2** | Автоматическая метрика |
| **R2** | **Структурная непрерывность** — кросс-главные ссылки разрешаются; утверждения не противоречат | Coherent + Validator | **L2** | Полуавтоматическая |
| **R3** | **Согласованность глоссария** — каждый термин одинаков по всем главам | Coherent | **L2** | Полуавтоматическая |
| **R4** | **Верность контуру + бюджет длины** — каждая глава доставляет обещание контура; длина ±20% бюджета | Validator | **L1/L2** | Полуавтоматическая |
| **R5** | **Плотность цитирования (УСЛОВНЫЙ)** — только если книга имеет библиографию | Validator | **L1/L2** | Механическая + ручная |
| **R6** | **Покрытие целевого читателя** — каждая глава обслуживает объявленного целевого читателя | Visionary + Validator | **L2** | Человеческое суждение + Flesch (R1) |

**R1-R4 — ядро.** R5 условен. R6 — суждение.

## Протокол RT-фаз для книг

### Четыре точки вызова RT

1. **RT-0 (Visionary соло, НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ):** тезис / жанровая коллизия / бюджет читательского времени.
2. **RT-1 (обязательный, полная пятёрка):** контур + план по главам + глоссарий + зависимости.
3. **RT-per-chapter-cluster (ОБЯЗАТЕЛЕН для L/XL, ОПЦИОНАЛЕН для M):** черновик главами. Builder пишет → Validator R1+R4 → Coherent R2+R3. FAIL блокирует следующий кластер.
4. **RT-2 (обязательный, перед подачей/публикацией):** все 6 R-проверок на полную рукопись + BL-19 если двуязычный.

### Конфигурация Builder

**Одиночный Builder по умолчанию**, глава за главой в порядке зависимости:
1. Перечитать план Analyst для главы C
2. Перечитать глоссарий (BL-29)
3. Grep предыдущих глав на ключевые термины (A_σ)
4. Написать главу C в полном бюджете длины
5. R1 (Flesch) локально
6. Проверка бюджета длины (±20%)
7. Если двуязычный: парная версия ПЕРЕД переходом к C+1 (BL-19)
8. R4 самопроверка (доставляет ли черновик обещание контура?)
9. Коммит главы C как один коммит (BL-24)
10. Перейти к C+1

**Исключение L/XL:** для XL-книги (>120 000 слов, >15 глав) Analyst МОЖЕТ разделить между 2-3 Builders по владению главами. Гейт Coherent ОБЯЗАТЕЛЕН между завершением каждого Builder и стартом Validator.

## Примеры (3 конкретных)

### Пример 1: Глоссарный дрифт между главами (R3 отказ Coherent, пойман на RT-2)

- **Сценарий:** Глоссарий определяет «агент» как «LLM-подпроцесс с собственным контекстным окном». Builder в Гл.3 использует «агент» в этом смысле. В Гл.7 «агент» дрифтует к RL-смыслу (автономный целеполагатель). Validator R1 по-главно — PASS. Coherent на RT-2 находит дрифт.
- **Роль-ловец:** **Coherent** (R3, глоссарный дрифт).
- **Исправление:** Унифицировать: пересмотреть Гл.7, ввести «автономный обучатель» для RL-концепта; или обновить глоссарий с двумя смыслами. Применить правило Yokoten: grep ВСЕХ глав.

### Пример 2: Расхождение контур-черновик (R4 отказ Validator, пойман на RT-per-cluster)

- **Сценарий:** Контур говорит Гл.5 покрывает: алгоритм X, скетч доказательства корректности, кейс-стади B с задачей Y (5 500 слов). Builder пишет Гл.5: алгоритм X + скетч доказательства — ОК, но кейс-стади B заменён на другой пример с задачей Z. 5 400 слов — в бюджете. Validator R4 ловит несоответствие.
- **Роль-ловец:** **Validator** (R4).
- **Исправление:** (a) Переписать Гл.5 с кейс-стади B (дефолт). (b) Обновить контур и каскадно проверить все нижестоящие главы (BL-11 ревью).

### Пример 3: Дрифт уровня Flesch между главами (R1 отказ Validator)

- **Сценарий:** Поп-наука книга, целевой Flesch-Kincaid = 9-10 класс. Гл.1 = 8, Гл.2-5 = 9-10, Гл.6 = 12, Гл.7-10 = 13-14. Среднее = 11.2. Дисперсия = 6 уровней. R1 ОТКАЗ + R6 ОТКАЗ.
- **Роль-ловец:** **Validator** (R1 + R6).
- **Исправление:** (a) Упростить Гл.6-10. (b) Пере-таргетировать читателя. (c) Разделить книгу на две.

### Book-специфичные BL (пространство BL-B — отдельный бюджет)

**BL-B1: ARC-релиз — деплой-событие (адаптация BL-2)**
Релиз Advance Reader Copy — релиз-событие. Требует: канарейку (10-50 бета-читателей), 7-дневное окно молчания, план отката.

**BL-B2: Верификация перед коммитом (адаптация BL-6)**
Перед коммитом черновика главы Builder ОБЯЗАН: (a) R1 (Flesch) в целевой полосе, (b) бюджет длины ±20%, (c) глоссарий перечитан, (d) компиляция (если объявлена).

**BL-B3: План эрраты/ретракции перед релизом (адаптация BL-14)**
(Примечание: BL-14 объединён в BL-8 в главном `BOOTSTRAP_LESSONS.md` 2026-04-20 как часть чеклиста deployment-event; BL-B3 сохраняет code_adapter-провенанс, т.к. `BOOTSTRAP_LESSONS_code_adapter.md` всё ещё определяет BL-14.)
Перед подачей рукописи издателю Builder ОБЯЗАН документировать план эрраты: кого контактировать, что содержит уведомление, процедура обновления.

**BL-B4: Библиография PRE-FLIGHT (УСЛОВНЫЙ — адаптация BL-22)**
УСЛОВНЫЙ — только если книга имеет библиографию. Перед RT-1 Analyst ОБЯЗАН проверить каждую ссылку: DOI/ISBN синтаксис валиден, для новых ссылок источник доступен и хотя бы один факт подтверждён.

### Итого BL: 22 + 2 + 4 = **28 BL**.

(BL-19 условный — активен только при `domain.bilingual: true`. BL-B4 условный — только при наличии библиографии.)
