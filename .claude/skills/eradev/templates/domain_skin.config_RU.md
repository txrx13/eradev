# Доменный скин: config

> Тип: config
> Модальность: text (равномерные веса 0.25 / 0.25 / 0.25 / 0.25 — v8-совместимый дефолт)
> OOD-область: text-discrete
> Родительские BL: BOOTSTRAP_LESSONS_universal.md (22 универсальных BL наследуется)
> НЕ наследует BOOTSTRAP_LESSONS_code_adapter.md
> Метод верификации: `parse` (синтаксический разбор + валидация схемы + скан секретов + кросс-конфиговая согласованность)
> Последнее обновление: 2026-04-11
> Вышестоящие роли: roles/{role}_EN.md
> Вышестоящая математика: eradev.md Section II.1 (веса B_text) + Section II.2 (v9 OOD-область)
> Живые эталонные конфиги: любой `projects/{PROJECT}/config.md` в дереве проектов (проекты предоставляют собственные примеры).

---

## Назначение / Когда META загружает этот скин

META загружает этот скин, когда `config.md` проекта объявляет:
- `domain.type: config`
- `domain.skin: templates/domain_skin.config.md`

При загрузке скин передаётся каждому порождённому ролевому агенту дополнительно к `roles/{role}_EN.md`. Он НЕ заменяет файл роли — предоставляет лёгкий мост словаря, переопределения фокуса, сильно расширенный протокол верификации `parse` (7 суб-проверок P1–P7), корректировки RT-фаз включая явный ярус RT-lite, примеры и таблицу BL, специфичную для конфигурационных артефактов.

**Область:** YAML, TOML, JSON, INI, `.env` и Markdown-fenced конфиги (напр., EraDev-конфиги проектов с `yaml`-fence внутри `.md`). Infrastructure-as-code манифесты (Kubernetes, Terraform, Ansible, systemd units) и определения схем входят в область этого скина как специализации общей формы «текст, привязанный к схеме».

## Маппинг словаря

Config-скин выполняет **ЛЁГКУЮ перезапись с ТЯЖЁЛЫМ расширением верификации**. Нагрузочные определения меняются вокруг ЧТО такое единица (пара ключ-значение, не функция), ЧТО означает верификация (parse + схема + секреты + кросс-конфиг), и КАК выглядят дефекты.

| # | Абстрактный термин | Значение в config | Где используется (обоснование) |
|---|---|---|---|
| 1 | **artifact** | конфиг-файл (`.yaml`, `.toml`, `.json`, `.ini`, `.env`, `.conf`) ИЛИ блок/стanza внутри, ИЛИ пара ключ-значение с контекстом приоритетности, ИЛИ YAML-fenced блок в Markdown | `analyst_EN.md` строка 7; `projects/{PROJECT}/config.md` часто использует yaml-fence внутри `.md` |
| 2 | **function** | пара ключ-значение — наименьшая адресуемая единица конфига (`port: 3000`, `debug: true`) | Аналог `builder_EN.md`; канонический вид пары ключ-значение вроде `type: code` внутри `domain:` |
| 3 | **module / file** | секция или стanza конфига — именованный блок связанных ключей (`domain:` в `projects/{PROJECT}/config.md`, `[server]` в TOML) | `projects/{PROJECT}/config.md` `domain:` стanza |
| 4 | **API / API endpoint** | определение схемы / интерфейсный контракт — объявленная форма, которой конфиг должен соответствовать (JSON Schema, OpenAPI, protobuf, CRD) | `analyst_EN.md` Обязанности 3; code-adapter BL-22 |
| 5 | **test / tests pass** | parse + валидация схемы + скан секретов + скан висячих ссылок — все механические проверки возвращают 0 | `validator_EN.md` Key Rules; Секция 4 этого скина |
| 6 | **verify** | запуск P1 + P2 + P3 + P4 — 4 механические суб-проверки | `analyst_EN.md` строка 24 |
| 7 | **validate** | запуск всех 7 parse суб-проверок (P1–P7), включая интерпретативные P5–P6 | `validator_EN.md` строка 7 |
| 8 | **build / compile** | parse — конфиг-файл читается парсером инструмента без синтаксической ошибки | Аналог code-скина `build` |
| 9 | **runtime** | время загрузки инструмента / время стартовой валидации — момент, когда целевой инструмент читает конфиг | `builder_EN.md` Key Rules 4 |
| 10 | **spec / specification** | СХЕМА — документированное или машиночитаемое описание допустимых ключей (JSON Schema, OpenAPI, protobuf, CRD, man-page) | `analyst_EN.md`; code-adapter BL-22 |
| 11 | **bug / defect** | синтаксическая ошибка ИЛИ нарушение схемы ИЛИ висячая ссылка ИЛИ инлайн-секрет ИЛИ конфликт приоритетности ИЛИ кросс-конфиговый дрифт — 6 классов отказов конфигов | `validator_EN.md` строка 20 |

## Переопределения фокуса ролей

### Visionary (фокус на config)
- **ПЕРВЫЙ якорь:** ЧТО конфигурируется (инструмент/подсистема/среда), КАКАЯ среда (dev/staging/prod/local), КАКОВА политика секретов. True North = *какой инструмент+среда обслуживается этим конфигом?*
- **Основной режим отказа:** Одобрение конфига без именования ВЕРСИИ СХЕМЫ.
- **Jidoka:** Q1 инструмент+версия НАЗВАНЫ? / Q2 среда явная? / Q3 политика секретов объявлена? / Q4 назначение дискретно или непрерывно?

### Analyst (фокус на config)
- **ПЕРВЫЙ якорь:** Прочитать СХЕМУ ИНСТРУМЕНТА. Прочитать СУЩЕСТВУЮЩИЕ конфиги проекта (BL-29). Прочитать цепочку приоритетности.
- **Определение артефакта:** Структурированный план с 9 обязательными частями: инструмент, схема, среда, уровень приоритетности, обязательные ключи, опциональные ключи, запрещённые ключи, секреты, кросс-конфиговые зависимости.
- **Основной режим отказа:** Построение конфига без чтения схемы.
- **Jidoka:** Q1 схема ПРОЧИТАНА? / Q2 перечисление ключей совпадает со схемой? / Q3 источники секретов указаны? / Q4 кросс-конфиговые зависимости указаны? / Q5 карта приоритетности явная?

### Builder (фокус на config)
- **ПЕРВЫЙ якорь:** Прочитать план Analyst. Прочитать схему. Прочитать существующие конфиги проекта для формата. Затем писать конфиг.
- **Определение артефакта:** Единый конфиг-файл. СОХРАНЁННЫЙ ФАЙЛ по каноническому пути, проходящий парсер.
- **Основной режим отказа:** Тихий коммит инлайн-секретов.
- **Вторичный:** Дрифт отступов.
- **Третичный:** Дубликаты ключей.
- **Четвёртый:** Опечатки в переменных окружения.
- **Jidoka:** Q1 план Analyst прочитан? / Q2 каждый ключ существует в схеме? / Q3 файл парсится? / Q4 скан секретов чист? / Q5 нет дубликатов ключей? / Q6 каждая ссылка `${VAR}` резолвится? / Q7 стиль отступов совпадает?

### Validator (фокус на config)
- **ПЕРВЫЙ якорь:** Прочитать план Analyst + конфиг-файл Builder. Запустить все 7 parse суб-проверок (P1–P7).
- **Определение артефакта:** Конфиг-файл КАК ЕГО УВИДИТ ИНСТРУМЕНТ — включая цепочку приоритетности в целевой среде.
- **Основной режим отказа:** Запуск только P1 и объявление PASS.
- **Jidoka:** Q1 все 7 P запущены? / Q2 версия схемы подтверждена? / Q3 предупреждения схемы прочитаны? / Q4 скан секретов запущен? / Q5 все ссылки env var разрешены? / Q6 кросс-конфиговые значения совпадают? / Q7 приоритетность проверена?

### Coherencer (фокус на config)
- **ПЕРВЫЙ якорь:** Прочитать конфиг + кросс-конфиговых соседей + глоссарий проекта (BL-29).
- **Определение артефакта:** Конфиг + (все другие конфиги с которыми он взаимодействует) = конфиг-система.
- **Основной режим отказа:** «Терминологический дрифт между конфигами» — один называет `hostname`, другой `host`, третий `server_host`.
- **Вторичный:** Фантомная когерентность — каждый конфиг валиден, но они расходятся в описании системы.
- **Jidoka:** Q1 единая конвенция именования? / Q2 одинаковые значения общих ресурсов? / Q3 одинаковые версии схем? / Q4 идентичность проекта согласована? / Q5 ссылки env var согласованы? / Q6 спот-чек 3 ключей?

## Протокол верификации (`parse` расширенный)

### Семь parse суб-проверок

| # | Проверка | Что обнаруживает | Кто | L1/L2 | Механизм |
|---|---|---|---|---|---|
| **P1** | **Parse синтаксис** — файл парсится чисто | Отступы, запятые, кавычки, табы/пробелы | Validator | **L1** | Механическая — `yq .`, `jq .`, `toml parse` |
| **P2** | **Валидация схемы** — файл проходит схему | Неизвестные ключи, неправильные типы, отсутствующие обязательные | Validator | **L1/L2** | Механическая если схема есть; интерпретативная иначе |
| **P3** | **Скан секретов** — нет инлайн-кредов | API-ключи, пароли, JWT, PEM-блоки | Validator + Coherencer | **L1** | Механическая — курируемый regex-список |
| **P4** | **Разрешение висячих ссылок** — `${VAR}`, `$VAR`, `<ref:key>` резолвятся | Опечатки в env var, отсутствующие vault-пути | Validator | **L1** | Механическая — grep + diff с целевым env |
| **P5** | **Здравость приоритетности** — при нескольких уровнях правило приоритетности однозначно | Тихие перекрытия, «почему моя настройка не работает?» | Validator | **L2** | Интерпретативная |
| **P6** | **Кросс-конфиговая согласованность** — 2+ конфига описывают ОДИН ресурс — значения совпадают | Дрифт портов, версий, эндпоинтов, хостнеймов | Coherencer | **L2** | Интерпретативная |
| **P7** | **Выравнивание версий схемы** — объявленная версия совпадает с используемыми ключами | Дефекты обновления версии инструмента; copy-paste старых конфигов | Validator | **L1/L2** | Механическая когда версия машиночитаема |

### Скан секретов (P3) — курируемый regex-список

```
- Общий паттерн паролей/секретов:  (password|passwd|pwd|secret|api_key|apikey|access_key|private_key|token|auth|credential)\s*[:=]\s*["']?[^\s"'{}$<>]{8,}["']?
- AWS access key:                    AKIA[0-9A-Z]{16}
- AWS secret key:                    (?<![0-9A-Za-z])[0-9a-zA-Z/+]{40}(?![0-9A-Za-z])
- GitHub token:                      ghp_[0-9A-Za-z]{36,}  |  gho_[0-9A-Za-z]{36,}  |  ghs_[0-9A-Za-z]{36,}  |  ghr_[0-9A-Za-z]{36,}
- OpenAI / Anthropic key:            sk-[A-Za-z0-9]{32,}  |  sk-ant-[A-Za-z0-9]{32,}
- Private key block:                 -----BEGIN (RSA |DSA |EC |OPENSSH )?PRIVATE KEY-----
- JWT token:                         ey[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}
- Bearer token:                      [Bb]earer\s+[A-Za-z0-9_\-\.=]{20,}
```

**Белый список плейсхолдеров:** `xxxxxxx`, `<your-api-key-here>`, `<your-api-key>`, `REPLACE_ME`, `REPLACE_ME_WITH_YOUR_KEY`, `${VARIABLE}`, `${ENV_VAR}`, `CHANGE_ME`, `your-secret-here`, `example-token`, `dummy-value`.

## Протокол RT-фаз для конфигов

### Точки вызова RT

1. **RT-0 (Visionary соло, РЕКОМЕНДУЕТСЯ):** захват назначения + политика секретов + версия схемы.
2. **RT-1 (ярус-зависимый — полная пятёрка ИЛИ RT-lite тройка):** перечисление ключей + написание + валидация.
3. **RT-2 (обязательный для prod/infra, опциональный для dev-local):** гейт перед деплоем. Полные 7 проверок + L2 интерпретативные (P5, P6).

### RT-lite vs полная пятёрка — дерево решений

```
Конфиг для production или инфраструктуры?
  production / staging / IaC / секреты / деплой-манифест / CI-секреты
    → ВСЕГДА полная пятёрка (независимо от размера)

Конфиг маленький (<50 строк) И чисто-данные (без секретов, без приоритетности, без кросс-конфига)?
  да → RT-lite (3 роли): Visionary + Builder + Validator

Конфиг средний (50-200 строк) ИЛИ имеет секреты ИЛИ приоритетность?
  да → Полная пятёрка

Конфиг большой (>200 строк) ИЛИ затрагивает несколько инструментов?
  да → Полная пятёрка с обязательным RT-2
```

### Пайплайн конфига (ФИКСИРОВАННЫЙ)

```
RT-0 (Visionary соло, РЕКОМЕНДУЕТСЯ) → назначение + среда + секреты + версия схемы
Решение по ярусу                      → RT-lite ИЛИ полная пятёрка
RT-1 (ярус-зависимый)                 → перечисление ключей Analyst (пропуск если RT-lite)
                                      → Builder пишет конфиг
                                      → Validator P1-P4 + P7 (L1 механические)
                                      → Coherencer кросс-конфиг (пропуск если RT-lite)
Гейт перед коммитом (BL-C2)          → парсер + скан секретов автоматически
RT-2 (обязателен prod/infra)          → полные 7 проверок + L2 интерпретативные
Коммит конфиг-файла                   → инструмент перезагружает / перезапускает
Объявление активации                  → пометка в деплой-логе (BL-C1)
```

## Примеры (3 конкретные задачи)

### Пример 1: Ошибка отступов YAML (P1 / P2)
- **Вход:** «Добавить блок `resources` под стanzy `services.api` в `docker-compose.yml`.»
- **Сценарий:** Builder использует 2-space отступ, файл использует 4-space. `limits:` на 1 уровень мелко. P1 ОТКАЗ — YAML интерпретирует `limits:` как соседа `services.api`.
- **Роль-ловец:** **Validator** (P1).
- **Исправление:** Переформатировать отступ на 4 пробела.
- **B-проверка:** F=0.7, E=0.9, (1-σ)=0.3, Λ=0.5 → B ≈ 0.60 ЖЁЛТЫЙ. После фикса B ≈ 0.90 ЗЕЛЁНЫЙ.

### Пример 2: Инлайн-секрет в `.env.example` (P3)
- **Вход:** «Создать `.env.example` документирующий переменные окружения.»
- **Сценарий:** Builder копирует реальный `OPENAI_API_KEY` из локального `.env` «для справки» и забывает заменить на плейсхолдер. P3 ОТКАЗ — паттерн `sk-[A-Za-z0-9]{32,}`.
- **Роль-ловец:** **Validator** (P3).
- **Исправление:** (1) Заменить на плейсхолдер. (2) Если закоммичено — РОТИРОВАТЬ ключ. (3) Установить BL-C2 pre-commit хук.
- **B-проверка:** F=0.6, E=0.8, (1-σ)=0.2, Λ=0.4 → B ≈ 0.50 ЖЁЛТЫЙ (КРАСНЫЙ при реальном ключе). После фикса B ≈ 0.88 ЗЕЛЁНЫЙ.

### Пример 3: Дрифт порта между конфигами (P6)
- **Вход:** «Настроить контейнеризованный сервис с `package.json`, `Dockerfile`, `docker-compose.yml`.»
- **Сценарий:** package.json: `PORT=3000`. Dockerfile: `EXPOSE 3001` (copy-paste из stackoverflow). docker-compose: `3000:3000`. Каждый файл парсится чисто. P6 ОТКАЗ — дрифт порта.
- **Роль-ловец:** **Coherencer** (P6).

## Known Out-of-Scope (OOD)

- **Runtime-изменяемое in-memory состояние** (Redis/Consul/etcd ключи как текущее состояние) — непрерывный поток, не text-discrete. OOD.
- **Непрерывная настройка runtime-параметров** (auto-scaler пороги, адаптивные rate limiters) — поток, не текст. OOD.
- **AI-driven hyper-parameter auto-configuration** — непрерывная оптимизация. OOD.
- **Сами события ротации секретов** (meta-config о политике ротации — в области; сама операция ротации — runtime). OOD.
- **Tool-specific DSL, которые на самом деле код** (Jenkinsfile, GitHub Actions с inline shell, Terraform `locals {}` с вызовами функций) — использовать code-скин.
- **Динамические контракты type coercion в JSON** — лучше `schema` или `protocol` модальность (v10).
