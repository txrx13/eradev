## Назначение / Когда META загружает этот скин

META загружает этот скин, когда `config.md` проекта объявляет `domain.type: article` и `domain.skin: templates/domain_skin.article.md`. Скин передаётся каждому ролевому агенту дополнительно к `roles/{role}_EN.md`. Он НЕ заменяет файл роли. Скин нацелен на статьи с теоремами/доказательствами/деривациями и эмпирические исследовательские статьи с цепочкой доказательства или деривационным скелетом, НЕ обзорные статьи, НЕ позиционные, НЕ нарративные эссе — см. «Known Out-of-Scope».

**Универсальность:** Этот скин корпус-агностичен. Он НЕ зашивает конкретный префикс имён файлов, конкретный движок набора, конкретный формат библиографии, конкретный глоссарий или конкретный двуязычный мандат. Проекты подставляют эти специализации через `domain.overlay:` (см. escape-поле overlay в `config.md`).

## Модальная B-формула (research-веса)

| Компонент | Вес | Обоснование |
|---|---|---|
| F (Фокус) | **0.30** | Обзор литературы + чтение преамбулы/эталона — доминантный гейт. |
| E (Выравнивание) | **0.20** | Выравнивание с интентом важно, но ограничено физической/логической корректностью. |
| (1-σ) (Согласованность) | **0.35** | **Доминантный.** Единственная логическая несогласованность в цепочке доказательства фальсифицирует весь результат. |
| Λ (Опыт) | **0.15** | Наименьший вес. Память помогает, но свежий обзор корпуса может холодно-стартовать новую статью. |

**Обоснование:** Научные статьи в scope «теорема/доказательство/деривация» предоминантно consistency-gated. Проверка библиографии — Focus-проверка; независимый пересчёт каждой формулы — Consistency-проверка. Эти веса ЗАКРЕПЛЕНЫ — не placeholder.

**Вариантное положение (вне scope этого скина):** Обзорные статьи и позиционные статьи ближе к creative-весам. Маршрутизация в `creative` скин (отложено) или reject.

## Переопределения фокуса ролей

### Visionary (фокус на статьях)

- **ПЕРВЫЙ якорь (A_F override):** Прочитать `thesis` и `abstract` предлагаемой статьи. Прочитать TOC корпуса (если проект ведёт). True North = *какое научное утверждение добавляет эта статья, и покрывает ли корпус это уже?*
- **Определение артефакта:** Центральное утверждение статьи + её позиция в корпусе. Не текст, не PDF — *аргумент*. На RT-0 Visionary говорит на уровне «эта статья доказывает X через Y, что дополняет/противоречит статье Z в корпусе».
- **Основной режим отказа:** Одобрение тезиса, дублирующего или противоречащего существующей корпусной статье БЕЗ явного подтверждения. Это **«корпусная коллизия»**. Митигация: Visionary должен перечислить 3 ближайших соседа в корпусе перед одобрением.
- **Jidoka (article-специализация):**
  - Q1: «Утверждение НОВОЕ, или статья N уже покрывает?»
  - Q2: «Тезис фальсифицируем проверяемым способом (AND-gate), или спекулятивный (FAILS OOD)?»
  - Q3: «Структура секций совпадает с gold-standard форматом проекта (если объявлен)?»

### Analyst (фокус на статьях)

- **ПЕРВЫЙ якорь (A_F override):** Прочитать выход *prior Check-First pipeline* статьи (см. Pre-Generation Checklist ниже). Если Check-First не выполнен — СТОП. Прочитать 3 ближайших соседа для терминологии+нотации (BL-29).
- **Определение артефакта:** Декомпозиция статьи по секциям: секция → утверждения → требование к источнику (какой cite) + требование к деривации (какой prior результат или постулат). Выход Analyst — таблица, не проза.
- **Основной режим отказа:** Пропуск Check-First («статья простая»). Нарушение BL-17. Митигация: Check-First СТРУКТУРНО ТРЕБУЕТСЯ; Jidoka A_F = 0.0 (ANDON) если не прочитан.
- **Jidoka (article-специализация):**
  - Q1: «Check-First пройден? NO → A_F=0.0 → Andon.»
  - Q2: «Для каждого утверждения — источник (идентификатор / corpus ref) или деривация (цепочка постулатов)?»
  - Q3: «Ресурсные конфликты с корпусом — один символ с разным значением?»
  - Q4: «Если проект мандатирует двуязычный набор, план каждой языковой версии с Шага 1 (BL-19)?»
- **Шаблон deliverable (article-specific):**
  ```
  ## Article Plan (выход Analyst для статей)
  Thesis: [одно предложение]
  Target corpus position: [какой пробел заполняет]
  Sections: I. [имя] | II. [имя] | ...
  Per-section claims table:
    Секция | Утверждение | Source/Derivation | Trust index (T1-T4) | Dependency
  Formula inventory: [список с precision / требованием пересчёта per project config]
  Bibliography deltas: [новые записи с проверенными идентификаторами]
  Bilingual plan (если проект требует): [какой язык первый, правило паритета]
  Check-First confirmation: [PASS/FAIL по пунктам]
  Pipeline: Check-First → draft → compile → проверки → commit
  Resource conflicts: [коллизии символов, нумерация, дрифт терминологии]
  System dependencies: [путь движка, конвертеров, шрифтов, bib DB]
  B-check: F=_ E=_ (1-σ)=_ Λ=_ → B=_
  ```

### Builder (фокус на статьях)

- **ПЕРВЫЙ якорь (A_F override):** Прочитать gold-standard reference проекта (статью, которую конфиг называет «format gold standard»). Прочитать 3 ближайших соседа для терминологии+нотации (BL-29). Прочитать mandatory preamble / template проекта (если объявлен). НЕ начинать прозу пока все чтения не завершены. BL-17 + BL-21 — АКТИВНЫЕ enforcement gates.
- **Определение артефакта:** Полный проектно-определённый набор артефактов. Для двуязычного проекта с множеством output-форматов это может быть 4–8 файлов; для одноязычного markdown-only проекта — 1–2 файла. Конфиг проекта определяет точный набор; Builder НЕ отмечает Done пока каждый объявленный файл не существует. Для двуязычных проектов — применение BL-19.
- **Основной режим отказа:** Черновик прозы напрямую в исходник без контура + таблицы утверждений + таблицы требований к источникам от Analyst. Митигация: Activation Operator Builder требует чтения плана Analyst ДО написания прозы.
- **Вторичный (только двуязычные проекты):** Черновик одного языка сначала, «другой потом». Нарушение BL-19. Митигация: по-секционный двуязычный ритм.
- **Третичный (опционально, project-defined):** Пропуск маркеров доказательств. Если конфиг проекта объявляет схему маркеров (напр., `[FACT]` / `[DERIVATION]` / `[HYPOTHESIS]` / `[OPEN]`), каждое существенное утверждение ДОЛЖНО нести маркер в исходнике. Если проект не объявляет такую схему, этот режим N/A.
- **Jidoka (article-специализация):**
  - Q1: «Gold-standard reference + 3 соседа прочитаны (F)?»
  - Q2: «Черновик совпадает с контуром+таблицей утверждений (E)?»
  - Q3: «Нет коллизий символов? Терминология по глоссарию проекта (если есть) (1-σ)?»
  - Q4: «Если проект объявляет маркеры — каждое существенное утверждение аннотировано (Λ)?»
  - Q5: «Если проект мандатирует двуязычный набор — каждая языковая версия секции перед переходом (BL-19)?»

### Validator (фокус на статьях)

- **ПЕРВЫЙ якорь (A_F override):** Прочитать план Analyst + полный набор артефактов Builder (любой missing файл — дефект 1). Прочитать проектный список проверок (см. проектный `config.md` для точного числа и владения). Validator владеет финальным гейтом для ВСЕХ проектно-объявленных проверок. Validator НЕ частично валидирует.
- **Определение артефакта:** Полный набор артефактов В ФИНАЛЬНОЙ ФОРМЕ — то, что увидит рецензент журнала. Validator симулирует рецензента в момент highest-stakes: перед подачей.
- **Основной режим отказа:** Запуск только cite_check и PASS, пока статья имеет фактуальные несогласованности, не уловленные cite_check (напр., «аннотация N=120, Таблица 2 N=118» — Пример 3). Validator должен запустить ВСЕ проектно-объявленные проверки.
- **Вторичный (если проект использует маркеры):** Доверие маркерам Builder без аудита. Митигация: Validator АУДИРУЕТ точность маркеров.
- **Jidoka (article-специализация):**
  - Q1: «Все проектно-объявленные проверки запущены, не только cite_check?»
  - Q2: «Для каждого fact/cited-маркера — цитата разрешается И источник поддерживает утверждение?»
  - Q3: «Для каждого derived-маркера — цепочка явная и полная?»
  - Q4: «Числа в аннотации, теле, таблицах, рисунках ВНУТРЕННЕ СОГЛАСОВАНЫ (C6a)?»

### Coherencer (фокус на статьях)

- **ПЕРВЫЙ якорь (A_F override):** Прочитать полный набор артефактов. Прочитать проектный глоссарий (если существует — `projects/{PROJECT}/glossary.md`). Прочитать 3 ближайших соседа. Coherencer заботится о *вписывании этой статьи в корпус*.
- **Определение артефакта:** Корпус + эта статья = новый корпус. L2 Coherencer работа.
- **Основной режим отказа:** «Глоссарный дрифт» — термин, определённый в глоссарии как X, используется со значением Y. Или коллизия символов. Или формула из статьи A с одним значением и в этой с другим. Все — (1-σ) failures на уровне корпуса.
- **Вторичный (если проект двуязычный):** Фантомная когерентность между языковыми версиями. Обе «согласны», но вводят одну и ту же ошибку. Митигация: независимая верификация выборки формул и цитирований.
- **Jidoka (article-специализация):**
  - Q1: «Каждый технический термин по глоссарию проекта (если есть) (BL-29)?»
  - Q2: «Коллизии символов с существующим корпусом?»
  - Q3: «Если цитируется формула из статьи N — совпадает дословно?»
  - Q4: «Если двуязычный — языковые версии структурно эквивалентны (секций, формул, цитирований, рисунков)?»
  - Q5: «Независимый spot-check 3 формул — пересчитать без чтения статьи?»
- **Правило двуязычной синхронизации (BL-19):** Если проект `bilingual: true`, Coherencer — ПРИНУДИТЕЛЬ правила language-parity. Коммит ЗАБЛОКИРОВАН если набор неполный ИЛИ размеры языковых версий расходятся >50%.

## Протокол верификации (cite_check расширенный)

Маппится на `domain.verify.method: cite_check` проектного `config.md`. Скин расширяет `cite_check` в 7 конкретных под-проверок, распределённых между Validator L1 (per-section / per-commit) и L2 (full-article / pre-submission).

### Семь cite_check проверок

| # | Проверка | Кто | L1/L2 | Механизм |
|---|---|---|---|---|
| **C1** | **Полнота библиографии** — каждая in-text цитата имеет matching запись; каждая запись цитирована >=1 раз | Validator | **L1** | Структурная grep-проверка |
| **C2** | **Атрибуция цитирования** — утверждение X, цитирующее источник S, действительно поддержано S (не просто упомянуто) | Validator | **L2** | Чтение источника (человек + LLM) |
| **C3** | **Синтаксическая валидность идентификаторов** — DOI, arXiv ID, URL, ISBN и др. | Validator | **L1** | Regex |
| **C4** | **Внутренние перекрёстные ссылки** — `§3.2`, `\ref{thm:main}`, `\eqref{eq:main}` и т.д. — разрешаются к реальной секции/теореме/формуле в том же исходнике | Validator | **L1** | Лог compile/render |
| **C5** | **Здравость самоцитирования** — каждое самоцитирование нагрузочно (не padding). Количественная лестница: 0-30% PASS / 30-50% NOTES / 50-70% NOTES ESCALATED / ≥70% FAIL | Validator + Coherencer | **L2** | Суждение + порог self_cite_rate |
| **C6a** | **Фактуальная согласованность** — числа в аннотации совпадают с телом, таблицами, рисунками | Validator | **L2** | Кросс-ссылочный скан |
| **C6b** | **Провенанс формул** — каждая нумерованная формула имеет Derived / Cited-with-pointer / Axiomatic / Conjectured маркер. Asserted-without-derivation = FAIL | Validator | **L2** | Классификация провенанса; `grep -B3 -A1 '<formula-tag>'` + ручное bucketing |

### Связь с проектным списком проверок

7 cite_check — SUBSET + EXTENSION проектного списка. Обычно проект объявляет дополнительные проверки (пересчёт, precision, no-fitting, plagiarism, AI-marker scans). Validator НЕ интерпретирует `verify.method: cite_check` как «только 7 cite_check». Section Verification — PARTIAL; полный гейт включает все проектно-объявленные проверки.

### Блок верификации

```
method:           cite_check
command:          гибрид — L1 (C1/C3/C4) автоматизируемы, L2 (C2/C5/C6a/C6b) — суждение Validator.
                  Compile step: проектно-определённый (tectonic / pdflatex / xelatex / pandoc /
                  typst / quarto / rmarkdown и т.д.).
success criteria: все 7 cite_check PASS И все проектно-объявленные проверки PASS
                  И каждый объявленный артефакт присутствует (BL-19 применяется iff project bilingual)
                  И документ компилируется чисто в каждом объявленном output.
                  C5 вердикт по количественной лестнице.
failure recovery: C1 → добавить запись ИЛИ цитирование; C2 → перечитать источник;
                  C3 → исправить синтаксис; C4 → исправить ссылку; C5 → обосновать;
                  C6a → выровнять числа; C6b → добавить деривацию / указатель / метку.
independence check: Validator НЕЗАВИСИМО пересчитывает выборку формул. Phantom coherence (BL-5).
```

### Референсная реализация (C1/C3/C4 L1, C2/C5/C6a/C6b L2)

Адаптировать regex под идиому цитирования проекта (`~[N]`, BibTeX `\cite{key}`, markdown `[@key]`, APA `(Author, Year)`). `SRC` — исходный файл.

```bash
# C1 — Полнота библиографии (регекс под идиому)
grep -oE '~\[[0-9]+(,\s*[0-9]+)*\]' "$SRC" | grep -oE '[0-9]+' | sort -u > /tmp/cites.txt
grep -oE '\\item\[\{\[[0-9]+\]\}\]' "$SRC" | grep -oE '[0-9]+' | sort -u > /tmp/biblio.txt
comm -23 /tmp/biblio.txt /tmp/cites.txt > /tmp/c1_orphans.txt
comm -13 /tmp/biblio.txt /tmp/cites.txt > /tmp/c1_dangling.txt
wc -l /tmp/c1_orphans.txt /tmp/c1_dangling.txt   # оба 0 = PASS

# C3 — Синтаксис идентификаторов
DOI_RX='10\.[0-9]{4,9}/[^[:space:]"}]+'
ARXIV_RX='(arXiv:)?[0-9]{4}\.[0-9]{4,5}(v[0-9]+)?'
grep -oE '(doi\.org/|DOI:?\s*)[^"[:space:]]+' "$SRC" | sed -E 's|.*doi\.org/||; s|^DOI:?\s*||' | grep -vE "$DOI_RX" > /tmp/c3_dois_invalid.txt
grep -oE "arXiv:[^[:space:]]+" "$SRC" | sed 's|^arXiv:||' | grep -vE "$ARXIV_RX" > /tmp/c3_arxiv_invalid.txt
wc -l /tmp/c3_dois_invalid.txt /tmp/c3_arxiv_invalid.txt   # оба 0 = PASS

# C4 — Внутренние перекрёстные ссылки (compile-лог)
"$COMPILER" "$SRC" 2>&1 | tee /tmp/c4_build.log
grep -cE 'undefined|multiply.defined|Citation .* undefined|could not find' /tmp/c4_build.log   # 0 = PASS
```

### Контракт размера выборки

`sample_size = max(3, ceil(sqrt(total_formulas)))`. Отбор ДЕТЕРМИНИРОВАННЫЙ. Обязательные включения: (1) формула из аннотации (если цитирует) — ловит abstract/body drift; (2) формула из main results; (3) формула из приложения/поздней секции. Оставшиеся слоты — непредставленные секции.

### Количественные пороги C5

- **0–30% → PASS.** Норма для single-author академических статей.
- **30–50% → PASS WITH NOTES.** Повышено — editorial review.
- **50–70% → PASS WITH NOTES ESCALATED.** Substantial — Builder ОБЯЗАН обосновать load-bearing роль каждого self-cite.
- **≥70% → FAIL.** Echo chamber. Require restructure ИЛИ Validator justification + Coherencer co-sign.

**Основа:** эмпирическая норма для peer-reviewed physics ~30%; single-author research corpora могут идти выше по конструкции. Проекты с намеренно выше self-cite profile могут сдвинуть пороги через overlay.

## PR-Gate (Publication Readiness, BL-A5 расширение Inv 17 publication-layer)

PR-Gate срабатывает ПОСЛЕ V-Gate (engineering validity, BL-A1..A4), но ДО
объявления артефакта «ready». BL-A5 = правило секвенирования: V-Gate ≠ PR-Gate.

V-Gate = набор cite_check + BL-A1..A4 выше (engineering validity: библиография, рендер, план ретракции, PRE-FLIGHT идентификаторов). V-Gate GREEN означает структурную целостность артефакта. Это НЕ означает publication-ready. PR-Gate — второй гейт, проверяющий публикационную поверхность: типографику, визуальный артефакт, декодируемость наивным читателем, стилистический паритет, аудит decision-log. Правило секвенирования (BL-A5): V-Gate ≠ PR-Gate; оба должны пройти; META НЕ ДОЛЖЕН объявлять «ready» только на V-Gate.

### PR-1 Визуальная инспекция артефакта (Validator ОБЯЗАН открыть отрендеренный PDF)
- Validator открывает отрендеренный PDF (или эквивалентный визуальный output), не только text source
- Проверки: типографические лигатуры корректны (em/en-dashes, smart quotes), рисунки рендерятся,
  перекрёстные ссылки разрешаются, citation slugs не литералы
- Tier: T3 checklist + T2-upgradable visual diff hook
- Отказ: ANDON, возврат Builder для исправления типографики

### PR-2 Тест наивного читателя
- Персона: внешний читатель, НЕ знающий project-internal slugs
- Читает аннотацию + введение: декодирует БЕЗ обращения к проектному глоссарию?
- Режим отказа: «slug citations в аннотации» (напр., [L-32], [BL-A2]) вместо
  полных имён + journal-style references
- Tier: T3 checklist (operator-side)

### PR-3 Стилистический паритет (между языковыми вариантами)
- Если domain.bilingual: true — RU/EN версии совпадают в стиле цитирования, типе тире,
  структуре параграфов
- Tier: T2 hook (расширение BL-19 bilingual sync)

### PR-4 Аудит decision-log
- Каждое Builder default (напр., выбор формы slug-цитирования) ДОЛЖЕН быть залогирован
- Coherencer ревьюит лог при PR-Gate; флагует «buried OD» (per Inv 16 OD-discipline
  расширение на non-rework решения)
- Tier: T3 checklist (ответственность Coherencer)

### Вердикт PR-Gate
- Все 4 PR-проверки ДОЛЖНЫ пройти до объявления «publication ready»
- B-score GREEN на V-Gate ≠ ready (см. meta.md GREEN ≢ ready amendment)
- META НЕ ДОЛЖЕН объявлять ready без явного PR-Gate PASS

## Протокол RT-фаз для статей

Три точки вызова RT:

1. **RT-0 (Visionary соло, РЕКОМЕНДУЕТСЯ):** тезис / корпусная коллизия. APPROVED / REJECTED / OUT-OF-SCOPE.
2. **RT-1 (обязательный, полная пятёрка):** контур + таблица утверждений + план Analyst. Builder НЕ начинает до одобрения.
3. **RT-2 (обязательный, перед подачей):** все проектно-объявленные проверки + 7 cite_check + bilingual set check (если проект двуязычный).

**Без RT между RT-1 и RT-2 для односекционных статей.** Для многосекционных (>4 секций) опциональный RT-1.5 после каждой секции.

### Одиночный Builder с по-секционным ритмом

Внутри одного Builder ритм:
1. Черновик секции I в primary-языке
2. (Если проект двуязычный) Черновик секции I в secondary-языке (BL-19)
3. Compile/render всех объявленных output-форматов
4. Аннотация маркерами (если проект объявляет)
5. Переход к секции I+1

**Исключение (только L/XL):** для XL-статьи (>8000 слов, >4 секций) Analyst может разделить между двумя Builders по владению секциями. Гейт Coherencer ОБЯЗАТЕЛЕН.

## Примеры (3 конкретных)

### Пример 1: Неподдержанное утверждение (C2 отказ)
- **Сценарий:** Builder цитирует `[Smith2020]` для `λ_L > 0` для всех observer states. Smith2020 доказывает это для подкласса (measurable phase space), не для всех.
- **Роль-ловец:** **Validator** (C2, L2, требует чтения источника). **Фаза:** RT-2.
- **Исправление:** (a) ослабить утверждение; (b) найти поддерживающий источник; (c) независимая деривация.
- **Почему cite_check один не ловит:** C1 PASS, C3 PASS. Только C2 (чтение источника) ловит.

### Пример 2: Противоречие контура (σ-отказ Coherencer)
- **Сценарий:** Секция III: «метрика — функционал информационного состояния наблюдателя». Секция V: «балковая метрика объективна, не зависит от наблюдателя». Взаимное противоречие.
- **Роль-ловец:** **Coherencer** (σ-спайк). **Фаза:** RT-1 (перед драфтом).
- **Исправление:** RT-1.5, Visionary уточняет нагрузочное определение, контур переписывается.
- **Маппинг словаря:** «observer-dependent metric» vs «observer-independent» = **symbol collision** (строка 22).

### Пример 3: Числовая несогласованность (C6a отказ)
- **Сценарий:** Аннотация: «120 симуляций». Секция IV: «N=120». Рис. 4: «N=120». Таблица 2: «118 наблюдателей». 120 запущено, 2 исключены по QC, исключение нигде не упомянуто.
- **Роль-ловец:** **Validator** (C6a, L2). **Фаза:** RT-2.
- **Исправление:** (a) обновить аннотацию/тело/рисунок: «120 запущено; 118 проанализировано»; (b) re-run; (c) пересмотреть критерий.
- **Почему C1-C5 один не ловит:** Ни одна не касается числовых фактов внутри статьи. Только C6a. Дидактический кейс для разложения cite_check на 7 под-проверок.

- **Спекулятивная философия.** Нет фальсифицируемого утверждения. OOD.
- **Real-time интервью / транскрипты.** Непрерывный поток. OOD.
- **Обзорные статьи / позиционные статьи.** Аргументная арка, не цепочка доказательства. Отложено в creative.
- **Блог-посты / op-eds.** Нет библиографии, нет обязательства доказательства. OOD — но агенты должны проверить, хочет ли оператор полного research-article rigor перед продолжением.
