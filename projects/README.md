# Как создать новый проект в EraDev

> **ВНИМАНИЕ:** Инстансы проектов живут в `<host-repo>/projects/{name}/`, НЕ здесь.
> Эта директория содержит только seed-шаблоны и документацию per-project.
> Файлы `config.md` и `lessons.md` каждого инстанса трекаются в директории
> `projects/{name}/` основного host-репозитория, а не в этом subrepo фреймворка.

## 1. Структура папки проекта

Создай директорию `projects/<project-name>/` со следующей структурой:

```
projects/<project-name>/
  MEMORY.md            # Память проекта (из MEMORY_TEMPLATE.md)
  spiral_log.md        # Спиральная память: витки Meta-Agent
  config.md            # Стек, порты, ноды, специфика проекта
  checklists/
    pre-commit.md      # Чеклист перед коммитом (из CHECKLIST.md, адаптировать)
    pre-deploy.md      # Чеклист перед деплоем (адаптировать под инфру)
    security.md        # Security baseline (из CHECKLIST.md, расширить)
  a3/                  # Папка для A3-шаблонов (postmortem)
  roles/               # Переопределения ролей, если нужны (опционально)
```

---

## 2. Инициализация MEMORY.md

1. Скопируй `eradev/MEMORY_TEMPLATE.md` в `projects/<project-name>/MEMORY.md`.
2. Заполни секцию "Железные правила" -- минимум 5, максимум 10.
3. Секции "Паттерны" и "Метрики" оставь пустыми -- они заполняются в процессе.
4. Запиши первое решение в Decision Log: "Инициализация проекта".

---

## 3. Инициализация spiral_log.md

Формат: каждый виток -- заголовок + дата, задача, результат, новые паттерны, метрики.
Виток 0 = "Инициализация". Каждый следующий добавляется В КОНЕЦ. Старые не редактируются.

```markdown
## Виток 0 -- Инициализация
- **Дата**: YYYY-MM-DD
- **Результат**: Структура создана
- **Метрики**: B=N/A, S_team=N/A
```

---

## 4. Заполнение config.md

Вынеси сюда ВСЮ проектную специфику. Промпты ролей НЕ должны содержать:
- Названия проекта (хардкод)
- IP-адресов и портов
- Технологического стека (Go/TS/Rust/Python)
- Путей к файлам проекта

Формат config.md: название, стек, репозиторий, ноды/порты (если есть), особенности.

---

## 5. Перенос паттернов из ядра

Ядро EraDev содержит универсальные паттерны (eradev/CHECKLIST.md).
Для проекта:

1. Скопируй релевантные секции из `eradev/CHECKLIST.md` в `checklists/`.
2. Адаптируй под стек: замени обобщенные пункты на конкретные команды.
3. Добавь проектно-специфичные пункты (порты, эндпоинты, DNS).
4. В MEMORY.md ссылайся на чеклисты: "см. checklists/pre-deploy.md".

Не дублируй чеклисты в нескольких местах. Один источник правды.

## 6. Адаптация ролей

По умолчанию используются 5 ролей из ядра EraDev. Для адаптации:

**Малый проект (1 человек + AI):**
- S-задачи: Builder + Validator (2 агента).
- M-задачи: все 5 ролей.

**Средний проект (команда):**
- Стандартные 5 ролей. При необходимости -- добавить DevOps-роль.

**Большой проект (несколько команд):**
- Иерархия Когерентов: L1 (внутри команды), L2 (между командами).
- Специализация Builder: Frontend Builder, Backend Builder, Infra Builder.

Если роль переопределяется -- создай файл в `projects/<project-name>/roles/`.
Формат: краткий промпт (до 150 строк), без дублирования ядра.

---

## 7. Чеклист готовности проекта

Перед началом работы убедись:

- [ ] `MEMORY.md` создан и содержит минимум 5 железных правил
- [ ] `spiral_log.md` создан с витком 0
- [ ] `config.md` заполнен (стек, репо, особенности)
- [ ] `checklists/` содержит адаптированные чеклисты
- [ ] `a3/` директория создана (пустая)
- [ ] Промпты ролей НЕ содержат хардкод проекта
- [ ] Decision Log содержит запись об инициализации

---

## 8. Framework-self проекты (F8 allow-list)

> Применимо только к проектам, живущим **внутри** репозитория `eradev/` (например `projects/eradev/`),
> а не к внешним host-инстансам.

Корневой `.gitignore` фреймворка по умолчанию исключает `projects/*`, чтобы host-проекты
не попадали в коммиты ядра. Для framework-self проектов (саморазвитие фреймворка) необходимо
добавить явный allow-list:

```gitignore
# allow framework-self projects
!projects/<name>/
!projects/<name>/**
```

**Чтобы добавить новый framework-self проект:** допиши `!projects/<name>/` (и при необходимости
`!projects/<name>/**`) в allow-list `.gitignore` корня фреймворка. Без этого `git status` не увидит
файлы внутри `projects/<name>/`, и trackable-артефакты (config, lessons, отчёты) выпадут из коммитов.
