# Доменный скин: code

> Тип: code
> Модальность: text (равномерные веса 0.25 / 0.25 / 0.25 / 0.25 — v8-совместимый дефолт)
> OOD-область: text-discrete
> Родительские BL-файлы: `BOOTSTRAP_LESSONS_universal.md` + `BOOTSTRAP_LESSONS_code_adapter.md` (30 итого = 22 универсальных + 8 code-adapter)
> Метод верификации: `build` (компиляция + тесты + линтер)
> Вышестоящие роли: `roles/{role}_EN.md` / `roles/{role}.md`
> Вышестоящая математика: `eradev.md` Section II.1 (веса B_text) + `eradev.md` Section II.2 (v9 OOD-область)

---

## Назначение

Это **скин-тождество** для модальности `code`. В отличие от скинов `article` / `book` / `research`, которые переписывают ролевой словарь для другого класса артефактов, code-скин практически ничего не делает: code — это модальность, для которой базовые файлы ролей были изначально написаны, поэтому абстрактный словарь (`artifact`, `verify`, `pipeline`, `produce`) уже напрямую соответствует кодовым понятиям. Этот файл существует для того, чтобы проектные конфиги с `domain.skin: templates/domain_skin.code.md` разрешались в реальный файл, а не в висячий указатель.

Code также является **ЕДИНСТВЕННОЙ модальностью, наследующей ОБА BL-файла**: `BOOTSTRAP_LESSONS_universal.md` (22 записи) И `BOOTSTRAP_LESSONS_code_adapter.md` (8 записей) = 30 итого. Не-кодовые модальности наследуют только универсальный файл.

---

## Маппинг словаря (Тождество — без переопределения)

Абстрактный словарь файлов ролей напрямую совпадает со словарём кода. Этот скин НЕ переписывает ни один термин. Агенты загружают базовый файл роли и интерпретируют каждый абстрактный термин в его кодовом значении ниже.

| Абстрактный термин (файл роли) | Значение в code |
|---|---|
| artifact | исходный файл (`.go`, `.py`, `.ts`, `.rs`, `.md`, `.yaml`, ...) |
| verify | компиляция + тесты + линтер + проверка типов |
| produce | написание/редактирование исходного файла |
| validate | запуск тестового набора, линтера, чекера типов, подтверждение прохождения CI |
| pipeline | редактирование → компиляция → тесты → линтер → коммит → пуш → деплой |
| deploy | git push в прод / мерж в main / CI-раскатка |
| component / module | пакет / модуль / директория |
| section / chapter | файл / функция / класс |

Эта таблица приведена ТОЛЬКО ДЛЯ ЯСНОСТИ АГЕНТОВ — базовые файлы ролей уже неявно используют эти кодовые интерпретации. Никакого переопределения словаря не применяется; скин документационно явен для согласованности со скинами `article` / `book` / `research`, которые ДЕЙСТВИТЕЛЬНО переопределяют.

## Переопределения фокуса ролей (Нет — см. базовые файлы ролей)

Code — базовая модальность. Каждая роль использует свой базовый файл без изменений. Переопределения фокуса для code дублировали бы содержание базового файла.

### Visionary
Без переопределения — см. `roles/visionary_EN.md` / `roles/visionary.md`. Стратегический вопрос: «какова Истинная Цель для этой кодовой базы, и какое предлагаемое изменение действительно к ней ведёт?»

### Analyst
Без переопределения — см. `roles/analyst_EN.md` / `roles/analyst.md`. Единица декомпозиции плана: функция, модуль, API-эндпоинт, тест-кейс. Граф зависимостей: импорты, сигнатуры типов, джойны схем.

### Builder
Без переопределения — см. `roles/builder_EN.md` / `roles/builder.md`. Протокол продакшена: BL-6 BUILD-VERIFY (компиляция/тесты перед коммитом). Гейт активации: A_F прочитать все изменённые файлы + соседние файлы в том же пакете. Выходной артефакт: исходный файл по каноническому пути.

### Validator
Без переопределения — см. `roles/validator_EN.md` / `roles/validator.md`. Протокол верификации: запустить полный набор тестов (юнит + интеграционные + E2E по применимости), линтер, чекер типов. Критерий успеха: все exit-коды 0; нет новых предупреждений; покрытие не регрессирует.

### Coherencer
Без переопределения — см. `roles/coherent_EN.md` / `roles/coherent.md`. Кросс-артефактная согласованность: API-схемы совпадают между продьюсером и консьюмером, терминология совпадает с глоссарием, BL-19 двуязычная синхронизация для документации. Детекция дрифта: grep на устаревшие символы, проверка на дублирующую логику, верификация паритета тест/прод.

## Протокол верификации (специфичный для code)

Напрямую соответствует `config.md` `domain.verify.method: build`.

```
method:           build
command:          (проектно-специфичный — напр., "go build ./... && go test ./..." или "pytest" или "npm run build && npm test")
success criteria: все команды сборки завершаются с кодом 0; все тесты проходят; линтер чист; чекер типов чист; нет новых предупреждений
failure recovery: исправить корневую причину (BL-3 FIX-TO-SPEC гейт — 3+ последовательных фиксов = СТОП, написать спецификацию, перезапустить RT-1)
independence check: Validator запускает пайплайн на чистом чекауте, не в рабочей области Builder; подтверждает тот же результат
```

Проектно-специфичные команды объявляются в `config.md` каждого проекта в поле `domain.verify.command` — скин не хардкодит их, потому что у каждой кодовой базы своя система сборки.

## Чеклисты

### Чеклист перед генерацией (BL-17 Check-First)
- [ ] Прочитать все файлы, которые будут изменены, ЦЕЛИКОМ (не только область дифа)
- [ ] Прочитать соседние файлы в том же пакете/модуле для понимания локальных соглашений
- [ ] Проверить интерфейсные контракты для любых кросс-модульных правок (сигнатуры типов, схемы, protobuf, API-контракты)
- [ ] Проверить существующие тесты для модифицированного пути кода — они всё ещё кодируют правильные инварианты?
- [ ] Для работы с внешними API: проверить эндпоинты ДО RT-1 (BL-22 PRE-FLIGHT гейт)

### Чеклист после генерации (BL-6 BUILD-VERIFY гейт, Jidoka)
- [ ] Сборка проходит (компиляция/проверка типов/линтер)
- [ ] Юнит-тесты проходят
- [ ] Интеграционные тесты проходят (если применимо)
- [ ] Нет новых предупреждений линтера
- [ ] Нет новых предупреждений об устаревании
- [ ] Git status показывает только ожидаемые изменённые файлы (нет случайного стейджинга)
- [ ] Сообщение коммита соответствует проектному соглашению

## Примеры (3 конкретные задачи)

### Пример 1: Исправление бага в `auth/login.ts`
- **Вход**: «Токен сессии не обновляется на мобильных браузерах»
- **Классификация домена**: type=code, modality=text, verify=build
- **Пайплайн**: A_F прочитать `auth/login.ts` + `auth/session.ts` + мобильный E2E-тест → воспроизвести баг → патч → `npm test` → `npm run build` → коммит → пуш
- **Ожидаемый артефакт**: правка `auth/login.ts` + возможно 1 новый тест-кейс в `auth/__tests__/`
- **Верификация**: `npm test` всё зелёное; `npm run build` exit 0; мобильный E2E-тест теперь проходит
- **B-проверка**: F=0.9 (прочитаны session + login + тест), E=0.9 (обновление токена = точный интент), 1-σ=0.9 (нет конфликта с контрактом сессии), Λ=0.8 (BL-17/BL-22 учтены) → B ≈ 0.87 ЗЕЛЁНЫЙ

### Пример 2: Рефакторинг `services/gateway` на типизированный middleware
- **Вход**: «Мигрировать обработчики запросов gateway на новый паттерн типизированного middleware»
- **Классификация домена**: type=code, modality=text, verify=build, blast_radius=MEDIUM
- **Пайплайн**: A_F прочитать `gateway/router.go` + `middleware/` + затронутые обработчики → план миграции → назначение владельцев файлов при нескольких Builder → рефакторинг обработчик-за-обработчиком → `go build ./...` + `go test ./...` после каждого обработчика → коммит на обработчик
- **Ожидаемый артефакт**: 5-15 файлов обработчиков + 1 файл middleware + обновлённые тесты
- **Верификация**: `go build ./...` exit 0; `go test ./...` всё зелёное; интеграционные тесты проходят; нет регрессии по латентности обработчиков
- **B-проверка**: F=0.9 (прочитаны все обработчики + контракт middleware), E=0.85 (типизированный middleware = точный интент), 1-σ=0.9 (контракт сохранён), Λ=0.8 (BL-24 one-commit-one-phase применён) → B ≈ 0.86 ЗЕЛЁНЫЙ

### Пример 3: Добавление нового gRPC-эндпоинта в `services/ai-provider`
- **Вход**: «Добавить новый эндпоинт `/v1/chat/completions`»
- **Классификация домена**: type=code, modality=text, verify=build, blast_radius=MEDIUM (смена протокола — BL-7 канарейка обязательна)
- **Пайплайн**: A_F прочитать `proto/*.proto` + существующие обработчики эндпоинтов + клиентские стабы → правка proto → перегенерация Go + Python стабов → реализация обработчика → написание теста → `go build ./...` + `pytest` → feature flag OFF → канарейка на 1 узле → мониторинг → роллинг → коммит
- **Ожидаемый артефакт**: 1 proto-файл, 2 перегенерированных стаб-файла, 1 файл обработчика, 1 файл теста, 1 конфиг-флаг
- **Верификация**: и Go, и Python стороны собираются; proto-контракт совпадает между продьюсером и консьюмером (BL-29 терминология + BL-28 контекст); метрики канарейки в пределах нормы
- **B-проверка**: F=0.9 (прочитаны proto + обработчик + клиент), E=0.9 (новый эндпоинт = точный интент), 1-σ=0.85 (контракт совпадает с обеих сторон), Λ=0.85 (BL-7 канарейка применена) → B ≈ 0.87 ЗЕЛЁНЫЙ

## Доменно-специфичные Bootstrap Lessons (code наследует все 8 CODE-ADAPTER BL)

Code — ЕДИНСТВЕННАЯ модальность, наследующая ОБА файла: `BOOTSTRAP_LESSONS_universal.md` (22 записи) И `BOOTSTRAP_LESSONS_code_adapter.md` (8 записей). Adapter-файл содержит:

- BL-2: Логи как ПЕРВИЧНЫЙ источник
- BL-3: FIX-TO-SPEC гейт (3+ последовательных фиксов = СТОП)
- BL-6: BUILD-VERIFY гейт (компиляция/тесты перед коммитом)
- BL-8: Смена протокола = канарейка обязательна
- BL-14: Гейт содержимого артефакта (соответствие формата, а не просто наличие)
- BL-22: PRE-FLIGHT эндпоинтов для внешних API
- BL-24: Один коммит = одна фаза
- BL-25: Радиус поражения определяет процесс

Свежий агент, бутстрапящийся на code-проекте, должен прочитать ОБА файла. Не-кодовые модальности должны читать только универсальный файл.

## Известные Out-of-Scope (OOD) для code-модальности

Задачи, которые выглядят как код, но на самом деле непрерывные или вне области v9 (`domain.ood_scope: continuous` → REJECT):

- **Потоковая передача в реальном времени / управление симуляцией** — нет терминального артефакта; «выход» — это непрерывный поток событий. Эскалировать к Visionary на Kill-Switch Level 2.
- **Настройка работающего сервиса** — подкручивание ручек на запущенном сервисе по непрерывным метрикам — это потоковая задача, а не text-discrete. OOD для v9.
- **Оптимизация по чат-тёрнам** — оптимизация поведения per-conversation-turn — это разговорная задача, а не code-артефакт. OOD для v9.

Агенты должны эскалировать их к Visionary RT-0, а не авто-продолжать. См. `eradev.md` Section II.2 для v9 OOD-реестра.

## Коррекция B-весов (дефолт — без переопределения)

Code-модальность использует дефолтные равномерные веса. Это v8-совместимый дефолт и инвариант обратной совместимости: `B_text(v9) ≡ B(v8)` для каждого pre-v9 code-проекта.

| Компонент | Вес | Обоснование |
|---|---|---|
| F | 0.25 | Файлы прочитаны, API проверены, типы поняты — всё одинаково важно для работающего кода |
| E | 0.25 | Выход соответствует интенту задачи (не только букве) |
| (1-σ) | 0.25 | Нет конфликтов с существующим кодом, архитектурой, типами, тестами |
| Λ | 0.25 | MEMORY.md просмотрен, прошлые паттерны применены, BL-1..BL-32 учтены |

Проекты МОГУТ переопределить эти веса в своём `config.md` секцией `## B-weight Override` (см. `projects/plugy/config.md` как живой пример — строгая работа с gRPC-контрактами повышает (1-σ)). Скин не переопределяет; проекты переопределяют индивидуально.
